# TEMPLATE-UPGRADE: 正式工程文档语言与表述规范

> 来源：模板维护者（2026-08-10 用户确认）
> 状态：2026-08-11 重新评估后扩写（规范本体 + 执行接入点 + 抗误伤边界）；待 PR #321 合并后归档
> 目标版本：`v1.60.5`
> Release impact：patch
> Release strategy：独立发布；不与命令预检或其他模板提案合并

## 1. 问题

模板已有文档追溯、状态词和生成流程规则，但缺少正式工程文档的统一语言规范，且现有生成 / 修改流程的执行节点不检查表述质量。AI 生成的需求、设计、技术方案和治理文档可能出现以下问题：

- 使用宣传口号、空泛抽象词或没有依据的评价。
- 为追求通俗而用日常比喻替代专业定义。
- 使用多层定语、连续从句和重复修饰，导致句子拗口。
- 混用术语、状态和约束强度，降低可审查性。
- 语言规范即使写在规则文件里，若不接入生成 / 修改的执行节点，也不会在每次输出时被对照检查。

## 2. 目标

1. 正式工程文档默认使用准确、专业、平实、简洁的书面语言。
2. 需求、结论和建议尽量落到明确对象、范围、条件、结果或验证方式。
3. 统一规范性用词、术语和状态表达，避免推测被写成事实。
4. 明确 `CHANGELOG-PLAIN.md`、README、教程等通俗表达场景的例外边界。
5. 把语言规范接入文档生成前 / 后、修改前 / 后的执行节点，使约束在每次输出时主动触发，而非被动加载。
6. 设置抗误伤边界，避免机械拦截误伤合法技术表达（行业术语比喻、愿景方向性表述、限定性修饰词等）。
7. 只约束新增和实际修改的内容，不触发历史文档批量改写。

## 3. 非目标

- 不新增独立的语言规范文件或规则层级。
- 不把示例词表做成关键词 CI 或 `check-template` 阻断断言；执行节点自检用问句式，不用关键词硬拦。
- 不要求所有句子采用同一固定句式或字符长度。
- 不禁止专业术语，也不要求用生活化比喻解释复杂概念。
- 不改写原始材料、法规、标准和外部文档的直接引用。
- 不改动 `ai/rules-core.md`：面向用户的决策说明（含大白话解释）保持原样，正式文档规范与对话式说明分离，互不波及。

## 4. 方案

两层：**规范本体**（global-rules §10）+ **执行接入点**（生成 / 修改流程节点）+ **抗误伤边界**。

### 4.1 规范本体

在 `ai/global-rules.md` 新增单一顶级章节 `§10 文档语言与表述规范`，不拆 `§10.1` 至 `§10.7`。章节采用一段适用范围说明、七条规则和一段生成后自检：

1. 准确、专业。
2. 平实、简洁。
3. 具体、可核对。
4. 逻辑和状态明确。
5. 规范性用词明确。
6. 避免不当表达。
7. 例外与渐进适用。

### 4.2 执行接入点（生成 / 修改前后自检）

`global-rules.md` 已在文档类任务的必读包（`ai/index.md` §3 / §4），§10 写入后规则可见性天然成立。但仅可见不够，需接入"逼 AI 主动对照检查"的执行节点。在以下节点各加一条问句式语言自检（"是否……若有，是否说明……"），不新增关键词 CI：

- `ai/document-lifecycle-rules.md` §10 生成前声明：声明块加"语言规范遵循 §10"。
- `ai/document-lifecycle-rules.md` §11 生成后自检：加语言表述自检项。
- `ai/prompts/docs/00-generate-or-complete-docs.md`【硬约束】：加第 19 条语言规范。
- `ai/prompts/docs/04-edit-single-doc.md` 修订要求：加第 18 条语言规范。
- `ai/prompts/review/10-docs-checklist.md` B 验收：加语言类 checkbox。
- `ai/prompts/review/24-docs-health-review.md`：四类信号扩为五类，加"表述语气"。
- `ai/document-lifecycle-rules.md` §1 基本原则：加第 8 条引用 §10。

这样 §10 从"被动加载"变为生成前声明遵循、生成后自检、修改前声明、修改后自检四时机闭环。

### 4.3 抗误伤边界

为避免规范误伤合法技术表达，§10 各条内置例外：

- 已成行业通用术语的比喻性表达（心跳、握手、沙箱、灰度、容器、管道等）视为专业术语，不受比喻限制。
- 愿景和路线图的方向性目标可使用方向性表述，但必须在需求或验收层落到可核对项。
- "尽量、最好、原则上"上下文已明确适用范围时可以使用，但不得作为回避具体承诺的模糊挡箭牌。
- 限定性修饰词（通常、一般情况下、在多数场景）属合理表达，仅删除空洞修饰。
- 有明确因果 / 条件 / 转折关系的复合句允许保留，仅避免无逻辑关联的多判断堆叠。
- 面向人的说明性文档（README、入门教程、操作说明、`CHANGELOG-PLAIN.md`、面向非技术用户的说明）可采用适度通俗表达。

## 5. 规范边界

- "需要"可用于描述客观依赖，不代替"必须 / 应 / 可以"等约束等级。
- "尽量、最好、原则上"上下文明确适用范围时可用，否则应说明条件或例外。
- "赋能、沉淀、闭环、全链路、能力建设"等词不是绝对禁用；使用时必须说明具体对象、动作、边界或结果。
- 已成行业通用术语的比喻（心跳 / 沙箱 / 灰度等）视为专业术语，不受比喻限制。
- 愿景 / 路线图可方向性表述，但须在需求或验收层落到可核对项。
- 行为、流程和要求应明确主体、对象、条件、动作和结果；概念定义与架构说明不强行套用同一句式。
- 决策、评审、建议和问题分析优先结论先行；其他文档按其信息结构组织。
- 非通用缩写首次出现时给出完整名称；代码标识符、协议标准名和业内通用缩写不随意翻译。

## 8. 完成标准

- 全局规则新增 §10 一个顶级章节，含七条规范与抗误伤边界，无多余子节或独立规则文件。
- 语言规范接入生成前 / 后、修改前 / 后的执行节点（问句式自检），四时机闭环。
- 专业术语、规范性用词、状态准确性、通俗表达例外与抗误伤边界均有明确约束。
- 不改动 `rules-core`，面向用户的决策说明与正式文档规范分离。
- 历史文档不被批量改写，后续修改时逐步应用新规范。
- 模板版本、changelog、提案归档和完整自检形成闭环。

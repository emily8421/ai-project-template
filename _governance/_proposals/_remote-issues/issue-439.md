# TEMPLATE-UPGRADE：阶段准出档位判据基准（stage exit level criteria，L0-L3）

## 1. 动机（去项目化）

AI 辅助开发走「先 MVP 后产品级」路线时，若「完成」没有可验证定义，生成物倾向退化为**表面系统**：有界面样子、无真实通道、错误路径缺失、权限靠前端隐藏、无验证证据。模板当前的地基与缺口：

**已有地基（本提案不重复建设）**：

- `ai/global-rules.md` §8.1：双维度阶段模型（功能范围 × 交付物形态）+ 三档推荐定义——但**每档只有一句话定义**，无可逐项核对的判据。
- `ai/document-lifecycle-rules.md` §2.1：阶段最小产物与出口对照（v1.71.0 落地）——管「每阶段**做什么产物**」，不管「产物**做到什么程度算哪一档**」。
- `ai/document-lifecycle-rules.md` §7.1：横切状态词典——可直接被引用，无需改动。
- `ai/doc-standards/09-verification.md` §3/§4：TC 状态枚举与验证文档规范——证据体系已备。

**缺口（本提案补）**：

1. **档位无判据**：三档一句话定义无法逐维度对照，「退出标准写多严」全凭执行 AI 自由发挥，同档不同 Phase 实际水位不可比。
2. **准出条目无强制证据形式**：「我觉得做完了」类无载体表述可通过验收。
3. **无机器约束**：判据文件被静默删除或退出标准指针被移除时，无任何检查报警。
4. **判据质量无校准机制**：判据写出来容易，是否「骗不过去」没有方法论保障——纸面自洽的判据照样放走表面系统。

## 1.1 与既有规则的关系（去重）

| 既有规则 | 关系类型 | 说明 |

## 2. 拟改（核心交付）

### 2.1 落地位置建议

- **新增 `ai/doc-standards/stage-exit-baseline.md`**（规范基线，同步件）：承载 §2.2~2.7 全部判据内容。
- **挂接 ×2**：`ai/global-rules.md` §8.1 三档定义处 + `ai/doc-standards/03-prd.md` 退出标准撰写处，各加一行指针。
- **可选机器约束**：`check-template` 结构检查加 advisory 断言（基准文件存在 + 03-prd 规范指针存在）；不做语义级检查（判据满足与否是人工/流程判断，无法机械化——与「六问不引入断言」同一力度判断）。

### 2.2 判据阶梯与及格线（L0-L3）

| 档 | 名称 | 一句话及格线 |
|---|---|---|
| L0 | 原型 / Demo | 主链路可演示；Mock / 内存允许但必须显式标注，不得虚标 |
| L1 | MVP / 试点 | 核心闭环真实可用：真实持久化、真实通道、后端权限、错误路径有处理有测试、可部署、需求→TC 闭合 |
| L2 | 可试用 / Beta | L1 全过 + 运维就绪：可观测基础（日志 / 健康检查 / 备份）、部署他人可照做、安全评审启动、验证数据可清理 |
| L3 | 产品级 / GA | 七维度全绿 + readiness gate 全 Go + 审计可追溯 + 故障可恢复 |

### 2.3 判据矩阵（7 维 × 4 档）

使用方法：准出判断 = 逐维度对照宣称档位的判据列；任一格不满足，即未达该档——须降档宣称，或补齐后重判。判据不适用项目形态时，须写明豁免理由，不得静默跳过。

| 维度 | L0 原型 / Demo | L1 MVP | L2 可试用 / Beta | L3 产品级 |
|---|---|---|---|---|
| D1 数据真实性 | Mock / 内存 / 写死数据允许，须标注并留替换条件 | 真实持久化，重启不丢；迁移 / seed / 回滚可重放 | 验证与演示数据同真实数据可区分、有清理口径；备份手段存在 | 留存 / 备份 / 恢复策略成文且演练过；数据生命周期（清理 / 归档）运营级 |
| D2 通道真实性 | 模拟通道允许，标注 Mock / 降级 | 真实通道已接入且已验证（真实请求→真实响应留证据） | 超时 / 重试有处理；外部依赖故障有已知降级 | 限流 / 监控 / 告警齐备；第三方变更兼容策略 |
| D3 错误与降级 | 主路径通；失败可见（禁静默吞错） | 关键失败路径有处理有测试；错误信息可见且不泄内部实现 | 降级路径成文（触发条件 / 用户影响 / 恢复条件）；健康检查存在 | 全路径覆盖 + 告警接入 + 故障可恢复（回滚） |
| D4 安全与权限 | 可豁免，必须标注缺口清单 | 权限由后端执行（直调接口须 401 / 403）；边界隔离实证（跨账号 / 跨资源零越权） | 安全评审启动（已知风险清单）；敏感操作有确认与审计痕迹 | 审计 / 脱敏 / 攻击面收敛成体系；合规项核查 |
| D5 测试与验证 | 主链 smoke + 截图 | 当前阶段需求→TC 闭合，含异常路径 TC；测试或等效自动门进 CI | 回归包可重复执行；关键用户流 E2E 自动化 | 全量回归 + 性能 / 容量基线；验证证据可审计追溯 |
| D6 部署与运行 | 本机可跑（步骤文档化） | 可部署到目标环境；配置外置（无写死环境值）；重装可恢复 | 部署文档他人可照做；日志 / 健康检查 / 备份可用 | 监控 / 告警 / 升级 / 回滚运营级；容量与恢复演练 |
| D7 文档追溯 | 场景→需求链成立 | 当前阶段需求→TC→证据全闭合；实现事实反向同步回文档 | 运行 / 操作文档（部署、故障处理）可用 | 运营 / 用户手册完整；文档健康度检查通过 |

**增量判据读法（回测产物）**：瘦客户端 / 宿主增益类形态（增量端的持久化 / 部署主体由宿主承担）下，D1「真实持久化」与 D6「可部署」按**增量判据**读——增量端只验自身新增面（如配置持久化、安装面），宿主侧引用既有证据。矩阵无需为形态差异开分支。

### 2.4 跨档位红线（任何档位不得违反）

1. 禁静默吞错（`ai/global-rules.md` §2.1 既有原则）。
2. 禁把 Mock、候选、预留、默认关闭写成真实、已接入、已启用（`ai/document-lifecycle-rules.md` §7.1 状态词典与传播规则）。
3. 禁前端隐藏入口、按钮禁用或路由守卫充当唯一权限边界；权限必须由后端接口与服务层执行（前端交互规范既有禁令）。
4. 禁无证据宣称通过；验证状态必须挂证据位置（`ai/doc-standards/09-verification.md` 既有要求）。
5. 兼容绕过（polyfill、逃生舱、临时闸）不计入缺陷修复完成，必须登记坑并留替换条件。

### 2.5 准出条目三要素与证据形式

每条准出条目（阶段退出标准条目、Sprint / 任务卡验收标准）必须同时包含三要素：

| 要素 | 要求 |
|---|---|
| 要求 | 做什么算数，对齐判据矩阵该档位判据 |
| 证据形式 | 从下方枚举中指明证据载体；不得使用「我觉得做完了」类无载体表述 |
| 状态词 | 对齐状态词典（已验证 / 已启用 / 降级 / Mock 等） |

证据形式枚举（只收现有体系产物，不新增报表）：

| 证据载体 | 说明 |
|---|---|
| 验证文档 TC 记录 | TC 矩阵状态 + 验收记录（含编号验证步骤与计数） |
| E2E 脚本与截图 | 过程证据（临时目录），收口时在验证文档引用其路径 |
| CI 门结论 | 代码健康门、集成测试、构建发布等 workflow 结论 |
| 演示 / 人工验收记录 | 验收记录行内的人工确认记载 |
| 迁移 / seed / 回滚脚本与执行记录 | 数据契约类判据的证据 |
| 服务器 / 环境侧审计与回传记录 | 运行环境态判据的证据（如清理 / 配置类 SQL 回传入库） |

### 2.6 反浮于表面对照表（通用检查表）

每行 = 一种 AI 造假 / 失真模式与当场拆穿方法（fail-closed）。来源项目以 9 个真实踩坑 / 正例案例校准过本表（案例含业务细节，不入正文；方法论实证见 §5）。

| 造假模式 | 拆穿方法（fail-closed） |
|---|---|
| 假持久化：内存 / 写死冒充存储 | 「重启后数据仍在」必须有重启断言测试或演示证据 |
| 假集成：写死返回冒充接通 | 真实请求→真实响应证据；未接通的通道状态词只能写 Mock |
| 假权限：前端藏按钮 | 直调接口必须 401 / 403，列入必测 TC |
| 只走 happy path | 错误路径必须有用例；无处理不得标完成 |
| 测试替身遮蔽 | 自动化 shim 与真实运行时语义必须核对；shim 绿不等于真实绿 |
| 门禁失效静默放行 | 确认门必须负向探测实证真实拦截 |
| 兼容绕过冒充修复 | polyfill / 绕过须登记坑并留替换条件，不计入修复完成 |
| 演示数据污染真实态 | seed / 验证数据与运行数据可区分，且有清理口径 |
| 环境假象误判 | 不可达 / 超时先复核实因再定性（休眠不等于故障） |

### 2.7 阶梯 ↔ 交付物形态标签映射

| 判据阶梯 | 交付物形态标签 | 关系 |
|---|---|---|
| L0 原型 / Demo | Demo | 等价 |
| L1 MVP / 试点 | MVP | 等价：核心闭环真实可用 |
| L2 可试用 / Beta | MVP（标签不变） | MVP 判据全过 + 运维就绪子集；对外宣称仍为 MVP |
| L3 产品级 / GA | 产品 | 等价 |

### 2.8 判据质量校准方法论（回测，随判据一起回流）

判据本身也需要防「纸面自洽」。建议基准文档附校准方法：

1. **五步流程**：草案（判据 + 反假表）→ **回测** → 转正（入规则 + 机器约束）→ 实战（随下一真实阶段退出标准生效）→ 回流（通用化上行，即本提案）。
2. **回测方法**：用**已完成阶段**的真实验收证据逐维度 × 逐阶段对照矩阵（「逐格对射」），每格二元出口——**修条目**（判据定得不合理，修订矩阵并留痕）或**记账**（当时验收确有洞，登记缺口，不得为过格而改写历史验收结论）。回测通过是转正前置门禁。
3. **力度**：回测是建议流程非强制门禁（模板层不强求各项目回测）；但「新判据须至少一次真实证据对照后才转正」作为起草建议写入基准文档。

### 2.9 独立裁决点：「可试用」是否升为正式标签（不与判据捆绑）

L2 判据随本提案落地使用，但「可试用 / Beta」是否升为模板正式交付物形态标签（涉及 `ai/global-rules.md` §8.1、`ai/doc-standards/03-prd.md` 双维度总览表等横切变更）交维护者独立裁决。**本提案不预设结论**：若不升，维持 §2.7 映射（L2 判据照用、对外宣称仍 MVP）；若升，另行小改标签枚举。来源项目当前选择「不升」。

## 5. 验证方式（来源项目实证摘要）

- **起草**：两份独立 AI 评估合并方案 → 判据矩阵 7 维 × 4 档 + 三要素 + 反假表 + 五步流程。
- **回测实证**：以来源项目两个已完成阶段的真实验收证据逐格对射（2 阶段 × 7 维 = 14 主格）：**修条目 0、记账 7**（预登记 4 + 在案 2 + 回测新发现 1），无一格靠改写历史验收结论过格；增量判据读法经瘦客户端形态实证成立。
- **转正实证**：判据转正为项目规则 + 结构检查进 CI，一次绿；此后判据文件 / 指针被静默移除时 CI 直接红（防删保护）。

### 2.1 质量门（示例补充，非新增规则）

- **原则**：项目必须声明适用的自动质量门（test / type / lint / build 按形态选择），不得只校验文档 / 版本 / 空白。
- **定位**：§6.2 已完整承接该口径（含「#332 固定三件套退回重写后与本口径统一」），本稿不再新增规则，仅建议补「常见形态对照」示例，帮助派生项目落地声明。
- **适用条件**：不适用项必须显式说明理由（如无类型系统语言 → type 不适用；build 已覆盖 type check → 不重复跑；CLI 脚本无独立 test → 说明验证替代方式；纯文档 Sprint 豁免）。
- **声明位置**：`ai/project-rules.md §5` 或 `docs/05-tech-spec.md`；CI 实际落地与声明一致。

### 2.2 关键 secret 启动校验（保留方向，补适用条件）

- **原则**：关键 secret（token 签名密钥、数据库凭证、第三方 API key 等）不得使用弱默认值；生产或安全敏感运行态启动期校验，缺失或为默认值即启动失败（fail-closed）。
- **适用条件**：本地开发、测试、显式 Mock 场景允许受控替代配置；豁免时点与理由必须写入技术方案与验证计划（`docs/05-tech-spec.md` / `docs/09-verification.md`），不得静默带弱默认运行。
- **机制**：具体校验实现（Settings 模块、环境变量检查等）由技术栈决定，模板不预置写法。
- **落点**：§6.2 应用说明块第 2 条。

### 2.3 多实现契约（保留方向，去语言绑定）

- **原则**：同一接口的多个可替换实现（demo / 真实、mock / prod、read-replica / primary）必须共享机器可检查的契约或兼容性测试，禁止仅靠 docstring + 鸭子类型声明接口对齐——否则新增方法只加到一个实现时另一实现静默缺失。
- **适用条件**：机制由技术栈决定（Python `typing.Protocol` / ABC、Java interface、TS interface + 契约测试等），模板不写死；契约变更须显式。
- **落点**：文本落在 §6.2 应用说明块第 3 条，指针回指 L0-12；不在 L0 正文新增。

### 2.4 候选落地文本（§6.2 应用说明块草案）

> **应用说明（来源：#332 退回重写稿）**
>
> 1. **质量门常见形态对照**：按 §6 主节与本节目口径，常见形态示例——有类型系统项目 → type 检查纳入质量门；build 已覆盖类型检查 → 不重复单跑；CLI / 脚本项目无独立测试命令 → 以 smoke / 手动验证替代并在声明中说明理由；纯文档 / 纯配置项目 → 豁免。
> 2. **关键 secret 启动校验（fail-closed）**：关键 secret（token 签名密钥、数据库凭证、第三方 API key 等）在生产或安全敏感运行态不得使用弱默认值；启动期校验，缺失或为默认值即启动失败。本地开发、测试、显式 Mock 场景允许受控替代配置，豁免时点与理由写入 `docs/05-tech-spec.md` 与验证计划，不得静默带弱默认运行。具体校验实现由技术栈决定，模板不预置写法。
> 3. **多实现显式契约**：同一接口的多个可替换实现（demo / 真实、mock / prod、read-replica / primary）须共享机器可检查的契约或兼容性测试，禁止仅靠 docstring + 鸭子类型声明接口对齐；机制由技术栈决定（如 Python `typing.Protocol` / ABC、Java interface、TS interface + 契约测试）。为 `global-rules §2.1` L0-12「先契约后实现」在多实现一致性场景的应用说明。

# TEMPLATE-UPGRADE：任务卡执行记录形态（task card execution record，照卡可接续）

## 1. 动机（去项目化）

模板的任务体系已覆盖「计划侧」：任务卡格式（`ai/global-rules.md` §3）与 Task 文件五要素（`ai/implementation-lifecycle-rules.md` §4.4）保证开工前知道「做什么、改哪里、怎么验收」；Sprint 完成包（§7.1）保证收口后回写计划与验证文档。但**执行过程中**的关键上下文在模板里没有入库位：

1. **「为什么这么做」不可考**：范围裁决（用户决策、边界收缩）、开工前对现状代码的核实结论，散落在会话上下文里，随会话消失；正式文档只留「做了什么」的收口结论。
2. **执行记录无结构**：§4.4 只要求「完成记录」存在——无叙事要素（遇到的问题 / 偏差与决定 / 验证计数），可审计性靠作者自觉，不同卡之间质量不可比。
3. **跨会话 / 跨机 / 跨 AI CLI 接手缺载体**：执行中状态默认在本地续接文件（gitignored，session-rules 明确不入库、不替代正式文档）；多 AI 协作或换机执行时，接手方只能靠会话外渠道交接或重新考古。

参照系（外部实例，已匿名化）：一独立项目采用「任务记录卡」形态——执行记录与代码同 commit 入库、第一读者设定为「下一个对该任务一无所知的 AI 会话」、收卡自检「换个一无所知的 AI 照卡能接续吗」。该形态经来源项目 6 个连续非平凡任务复现验证（见 §5），机制可用且值得模板化。

**缺口（本提案补）**：把任务卡执行记录从「作者自觉」升级为「有结构、有入库定位、有接续自检」的默认形态。

## 1.1 与既有规则的关系（去重）

| `ai/implementation-lifecycle-rules.md` §4.3（拆卡触发条件） | **被引用，不改动** | 「非平凡任务」判定沿用既有触发条件，不新增拆卡门槛 |

| `ai/implementation-lifecycle-rules.md` §5.1（设计可驱动性六问，#407 落地） | **互补，提供卡级留痕位** | 六问答「设计够不够开工」；技术事实基线记「代码现状是什么」；六问结论可在卡内登记（比计划文档声明处更贴近执行的留痕位，两者并存不冲突） |

| `ai/session-rules.md`（本地续接文件不入库） | **边界互补，不合并** | 续接文件管会话间临时续接（gitignored）；任务卡执行记录管入库可审计记录——同一段工作的两个侧面，不互相替代 |

**本提案不含**：交接开工检查三层（交付证据机械核对 / 语义核对 / 直接依赖核对）——来源项目零实证，按「实践复用一次才升规范」继续暂缓观察，留待后续独立评估。

## 2. 拟改（核心交付）

### 2.1 落地位置建议

- **`ai/implementation-lifecycle-rules.md` §4 新增一小节**（建议 §4.5「任务卡执行记录形态」）：承载 §2.2 内容。
- **挂接 ×1**：§4.4「完成记录」要素处加一行指针（完成记录按新小节结构化；非平凡任务默认适用）。
- **不新增脚本 / CI 断言**：记录结构与可接续性是语义判断，无法机械化——与六问（不引入断言）、观察日志（不引入门禁）同一力度判断。

### 2.2 任务卡执行记录形态（四项内容标准 + 一项自检）

适用：§4.3 触发条件拆出的非平凡任务卡。轻量任务（单点修复、纯文档收口等）可裁剪，建议留一行说明裁剪了哪些项——形态随任务重量自适应，不搞一刀切。

1. **范围决策记录**：任务的裁决点（用户决策、边界收缩、方案取舍）在卡内留痕——决策点、结论、适用范围；作为「AI 不可自主扩展需求」（`ai/global-rules.md` §1）的执行侧证据。
2. **开工前技术事实基线**：编码前对将触碰模块的核实结论（现状行为、关键约束、已知坑），一行一事实、注明核实日期；防「文档声明 ≠ 运行时行为」类返工。与六问分工：六问核设计完备性，事实基线记代码现状。
3. **完成记录叙事结构**（把 §4.4「完成记录」具体化，五要素）：
   - 实现记录（做了什么 + 提交 / PR 锚点）；
   - 遇到的问题（坑与当场修复方式）；
   - 偏差与决定（实现偏差 vs 设计缺口的二分处置结果，衔接 §5.1 既有口径）；
   - 验证结果（命令 + 通过计数 + 失败项）；
   - 残留（未决项与下一步）。
4. **自包含执行节（可选，多机 / 跨环境协作形态）**：需移交其他机器、环境或会话执行的步骤，写成自包含节——步骤、命令 / 脚本、证据回填位齐备，执行侧直接在卡内回填执行记录，不依赖执行侧的本地会话文件。
5. **入库定位与可接续自检**：任务卡（含执行记录）随实现**同一 PR 入库**，不滞留会话本地；收卡自检一句——「换个一无所知的 AI，只读这张卡和仓库，能接续吗」——不能则补卡后再收。

### 2.3 力度

**建议 + 默认**：非平凡任务卡默认采用本形态；项目可在 `ai/project-rules.md` 细化或声明豁免；不设机器门禁。

## 3. 版本影响

建议 **MINOR**：`implementation-lifecycle-rules.md` 增一小节 + 指针一处；不改既有规则语义、不加 CI 断言，不破坏既有项目流程。

## 4. 影响面

- 修改：`ai/implementation-lifecycle-rules.md` ×1（新增小节 + §4.4 指针）。
- 对派生项目：新拆卡任务默认按本形态记录；存量任务卡不回溯改写。
- 不新增需求 / 表 / 接口 / 验收目标，不新增工具链依赖。

## 5. 验证方式（来源项目实证摘要）

- **形态实证**：来源项目连续 6 个非平凡任务卡按本形态入库（卡随实现同 PR）；其中 4 卡为完整形态（元信息 / 范围决策 / 技术事实基线 / 完成记录叙事齐备），2 卡（PoC 计划卡、文档收口卡）自然裁剪为轻量变体——形态随任务重量自适应，与 §2.3 力度设计一致。
- **跨机接续实证**：3 卡含自包含执行节，由另一台机器直接执行并在卡内回填记录（只读核对 → 真执行 → 复核回填，含多轮 dry-run 记录与补遗），开发机经 git 拉取消化——全程零会话外渠道传递。
- **审计证据实证**：一次判据回测（2 阶段 × 7 维 = 14 格对射）以任务卡完成记录为唯一过程证据源完成——卡可独立充当审计证据。
- **未提交**：无脚本 / CI 改动；纯规则文本。

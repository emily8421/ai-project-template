# TEMPLATE-UPGRADE：设计→编码放行「可驱动性六问」+ 占位/降级豁免边界 + 偏差二分（design-to-code codability gate）

## 1. 动机（去项目化）

模板现有链路中，「详细设计是否足以开工编码」缺少一个可操作的判据：

- `ai/document-lifecycle-rules.md` §2 E4（详细设计→实现计划）是**阶段级**评估：管「这批设计文档整体能否进入计划阶段」，不做逐模块完备性检查；
- `ai/implementation-lifecycle-rules.md` §5（单任务执行规则）要求任务开工时声明「上游依据：关联 REQ、Phase、设计章节」，但只要求**引用存在**，不要求**被引用的设计足以指导编码**——设计章节写了职责却没写错误语义、写了接口名却没写失败形态时，任务照样能合规开工，缺口在编码中后段才暴露（返工、AI 自行脑补设计）。

参照实例（另一独立软件项目，面向对象方法、单机桌面形态）在其开发过程规范中沉淀了**编码可驱动性六问**作为设计→编码的放行判据，经 2 个里程碑 + 多次复检实测迭代（v0.1→v0.2，含两次实战教训回填），核心内容：

> 详细设计进入编码前逐项回答：①**接口契约**（谁调用、传入什么、返回什么、失败如何表达）②**内部结构**（类、模块、状态或职责如何组织）③**算法逻辑**（规则、步骤、分支、优先级和降级语义）④**数据进出**（数据从哪里来、经过什么处理、到哪里去）⑤**错误处理**（各类失败如何检测、呈现、恢复或升级人工处理）⑥**验证基准**（用什么样例、真值、断言或检查证明实现正确）。
> 六问存在任一未回答项时，不得宣告该模块可驱动编码。

三条配套规则同样来自实战教训，价值不低于六问本体：

1. **占位豁免边界**：依赖未就绪的占位模块可暂缓内部部分（②③⑥的模块内部细节），但**跨层契约面（①④⑤）任何时候不得随占位豁免**——契约面是跨层横切物，其缺口会在依赖模块启动时才暴露（实例教训：界面占位期未检接口映射，覆盖 4/9 屏，S3 前才补）。
2. **降级态≠免检态**：必交付的降级形态（如外部服务未接入时的简化运行）同样必须过契约面检查——降级态是交付物的一部分（实例教训：AI 助手降级方案的接口形状/引导内容/验收判据三缺）。
3. **实现偏差 vs 设计缺口二分**：编码中发现与设计不符时，先判定是实现偏差（实现侧可修正，改代码对齐）还是设计缺口（驱动依据不足，停任务走变更机制回设计补足后再继续），不得在代码里自行发明设计。

## 2. 拟改

### 2.1 `ai/implementation-lifecycle-rules.md` 新增「设计可驱动性检查」节（核心）

位置建议：§5（单任务执行规则）之前或并入 §3（阶段规划规则）末尾。内容要点（示意措辞，落地时可微调）：

> **设计可驱动性六问**：每个待实现模块（`docs/design/*` 子系统或 Sprint 内非平凡构件）进入编码前，其设计文档必须能逐项回答：接口契约 / 内部结构 / 算法逻辑 / 数据进出 / 错误处理 / 验证基准六问；检验方式=每问在设计中定位到具体产物位置（章节 / 图 ID / 表），不凭印象。任一问无答=不可驱动，先补设计再开工；⚠️ 缺口须显式登记补齐口径（如 DDL 字段级留编码期落），不构成阻塞但要在 Sprint 输入文档注明。
>
> **占位与降级豁免边界**：依赖未就绪的占位模块可暂缓②③⑥的模块内部细节，但①④⑤（跨层契约面）不得随占位豁免；必交付的降级态同样过契约面检查（降级态≠免检态）。豁免必须显式登记（哪个模块、豁免哪几问、替代依据是什么），不得整体豁免。
>
> **偏差二分**：编码中发现实现与设计不符，先判定「实现偏差」（改代码对齐设计）或「设计缺口」（停任务，按变更传播规则更新设计后再继续），不得在代码里自行发明设计。处置结果回写任务记录或 `docs/design/*` 实现偏差区（与既有 E6 反向同步衔接）。

### 2.2 触发与力度

- **触发**：Sprint 涉及非平凡模块编码前（对应 E4 之后的单模块粒度）；Lean / 小工具项目可裁剪，须在 `ai/project-rules.md` §3 声明。
- **力度**：与 §13 图表规范同口径——「建议 + 默认」而非强制门禁；不引入 check-template 断言（六问是否有答是语义判断，无法机械化）。Sprint 计划（08）中该模块的「输入文档」声明处可挂六问结论（可驱动 / ⚠️ 清单）作为轻量留痕。

## 4. 与既有规则的关系（去重）

- **E4（详细设计→实现计划评估）**：E4 管阶段级转换（这批设计能否进入计划），六问管单模块完备性（这个模块能否开工）；层级互补，六问是 E4 通过后的下一道粒度。
- **`implementation-lifecycle-rules` §5 上游依据**：§5 要求引用设计章节，六问要求被引章节足以指导编码；前者管「有没有引」，后者管「引的东西够不够」。
- **§3 System Skeleton Gate**：骨架先行管「首个业务 Sprint 前有可运行框架」，六问管「每个模块编码前设计完备」；时序不同（Gate 一次，六问逐模块），互补。
- **E6 反向同步落点约束**：偏差二分是 E6 的前置工序（先定因再决定改码还是回设计），落点仍走 E6 既有约束，不重复定义。
- **`global-rules` §2.1 L0-12「先契约后实现」**：L0-12 是编码期通用原则（对外接口先定义），六问是设计期放行判据（设计的六个维度完备才开工）；阶段不同，粒度不同。
- **`doc-standards/design-doc.md` 详细设计要素**：其要素清单（流程/状态机/失败降级/readiness gate/验收追溯）与六问内容大量重叠——六问不另立要素清单，作为「这些要素是否足以开工」的检查视角挂接；落地时在 design-doc.md 头部加一行指针即可，不双写。

## 5. 影响面

- 修改：`ai/implementation-lifecycle-rules.md`（新增一节）；`ai/doc-standards/08-dev-plan.md`（「输入文档」字段一句可选挂接）；`ai/doc-standards/design-doc.md`（头部一行指针，可选）；
- 不改：E1-E6 评估码、System Skeleton Gate、§5 单任务执行规则语义、脚本与 CI；
- 下行同步后存量派生仓不强制回溯补检（新 Sprint 起自然适用）。

## 6. 验证方式

- 模板仓：文档审阅 + check-template 自检；
- 实例佐证：参照实例两个里程碑实测（M1-M4 六问齐→可驱动；M5/M6 占位经豁免边界规则补齐后才放行）+ 其「判据记录宽于事实」对账事件的补正记录；提案来源仓（LUMEN）首个适用 Sprint 试点后回填结论。

# 工作空间根目录结构评估与整理建议（gpt-5.6-terra）

> 定位：调研记录。本文记录对参考工作空间目录的只读观察与 AI 建议，不改变当前模板的目录契约，也不构成已批准的迁移方案。

## 1. 目的与范围

目标是在不牺牲模板方法论和同步能力的前提下，评估如何让项目代码及其实现配套材料拥有单一、可直接复制的入口。

本次仅检查了以下范围：

- 参考工作空间 `D:\2-Project\7-Plugin\miiot_plugin_develop_system` 的根目录、两层目录清单、根入口说明、`_workspace/` 治理文件索引，以及 `flowkit/` 的工程入口信息。
- 本仓库的根目录、两层目录清单、`README.md`、`docs/README.md` 和代码骨架说明。

未读取参考工作空间各目录下的完整业务内容；本文不对其内容质量、Git 状态或跨目录约束的实际执行效果作结论。

## 2. 已核实观察

### 2.1 参考工作空间

参考工作空间将根目录分为清晰的领域入口：

```text
miiot_plugin_develop_system/
├─ 01-文档/             # 业务文档
├─ 02-数据/             # 数据源登记与索引
├─ 03-知识输入/         # 只读参考依据
├─ 04-工具/             # 工具与脚本治理
├─ flowkit/              # 唯一应用代码入口
└─ _workspace/           # 跨目录治理、索引、会话与挂载登记
```

其核心价值不在于目录名前的编号，而在于职责边界直观：

- `flowkit/` 被明确登记为“代码”挂载项，是应用代码的单一入口。
- 文档、数据登记、知识输入、工具与跨目录治理互相分离。
- `_workspace/` 承担目录地图、跨目录约束、Git 与会话续接等横切治理，不与应用代码混放。
- 数据目录的说明明确区分“数据源登记”与“数据本体”，有利于避免大体积或敏感数据进入工作区仓库。

### 2.2 当前模板仓库

当前根目录同时包含三类内容：

- 模板方法论：`ai/`、`template-docs/`、`scripts/`、`template-sync.json`、维护手册。
- 模板治理记录：`ai-records/`、`sync-records/`、`_proposals/`、`.ai/`。
- 可供派生项目使用的项目产出骨架：`docs/`、`frontend/`、`backend/`、`tests/`、`docker/`、`tasks/`。

这种布局适合维护模板本身，但对“只取实现所需目录”的使用者不够直接：代码骨架、项目文档和项目脚本与模板治理材料处于同一根层级，复制时需要人工识别排除项。

## 3. 结论

建议借鉴参考工作空间的“单一实现入口”原则，但不直接复制其编号目录、多 Git 仓或工作区挂载机制。

本仓库是模板仓，`ai/`、`template-docs/`、`scripts/` 与 `template-sync.json` 已存在同步和自检契约。直接将这些目录改名或移动到编号目录会扩大同步脚本、文档链接、派生仓继承和自检断言的影响面，风险高于收益。

更合适的方向是新增一个明确的项目产出容器，将未来派生项目真正需要复制和实现的内容收拢其中；模板方法论与模板治理仍保持独立。

## 4. 建议目标结构

建议的概念分区如下，目录名可在确认后再定：

```text
ai-project-template/
├─ project/                         # 派生项目可复制的单一入口
│  ├─ docs/                         # 项目事实与项目设计
│  ├─ src/                          # 代码实现入口
│  │  ├─ frontend/                  # 按项目形态启用
│  │  ├─ backend/                   # 按项目形态启用
│  │  └─ packages/                  # 共享库，按需启用
│  ├─ tests/                        # 项目测试
│  ├─ tools/                        # 项目运行、开发、数据处理脚本
│  ├─ docker/                       # 项目运行与部署辅助
│  ├─ data/                         # 数据说明、样例和索引；数据本体按规则外置
│  ├─ tasks/                        # 项目任务单
│  └─ README.md                     # 项目使用与交付入口
├─ ai/                              # 模板方法论与 AI 行为规范
├─ template-docs/                   # 模板手册、脚手架与 profile
├─ scripts/                         # 模板同步、校验和脚手架脚本
├─ ai-records/                      # 模板治理记录
├─ sync-records/                    # 同步过程记录
├─ _proposals/                      # 模板改进提案
├─ _examples/                       # 独立示例，不混入 project/
├─ _archive/                        # 历史归档
├─ template-sync.json
└─ README.md
```

### 4.1 关键设计原则

1. `project/` 是唯一的交付复制入口。需要一个项目时，使用者可以复制该目录，不必携带模板维护和治理材料。
2. `src/` 仅包含实现代码。前端、后端和共享包以子目录区分，避免 `frontend/`、`backend/`、`tests/` 在模板根目录分散。
3. `tools/` 与模板 `scripts/` 分离。前者服务于派生项目，后者服务于模板维护、同步和自检。
4. `data/` 默认只保存索引、样例、模式定义和脱敏测试夹具；原始、敏感或大体积数据必须有外置位置和登记规则。
5. 文档保留在 `project/docs/`，继续遵守现有 `00-09` 核心文档及子目录分区规则，不将业务文档拆散到根目录编号区。
6. `ai/`、`template-docs/`、模板 `scripts/`、治理记录与项目产出之间保持显式边界，降低模板同步覆盖项目实现的风险。

## 5. 可选方案比较

| 方案 | 做法 | 优点 | 主要代价 | 建议 |
|---|---|---|---|---|
| A. 维持现状 | 继续在根目录保留各代码骨架 | 对现有链接、同步与自检零影响 | 复制项目时仍需手工筛选 | 不满足本次核心目标 |
| B. 新增 `project/` 容器 | 逐步将项目产出骨架移入 `project/` | 单一复制入口清晰，保留模板层稳定性 | 需要系统迁移路径与兼容期 | 推荐 |
| C. 全面编号化根目录 | 把模板、代码、文档、记录都改为 `01-*` 等 | 视觉上整齐 | 同步契约、引用和脚本影响面很大 | 不建议 |
| D. 仅建立复制清单 | 不改路径，只维护“复制这些目录”的文档或脚本 | 迁移成本低 | 仍不是真实单一入口，清单易漂移 | 可作为 B 的过渡措施 |

## 6. 推荐推进顺序

1. 先确认 `project/` 是否作为正式名称，以及它是“派生项目模板”还是“本仓唯一可运行示例”。这是目录语义的关键分歧。
2. 建立迁移清单：现有根目录中哪些项目产出应迁入，哪些必须留在模板层，哪些只应存在于 `_examples/`。
3. 审计 `template-sync.json`、同步脚本、自检脚本、README 链接、示例脚本和派生仓预期路径，形成完整影响矩阵。
4. 设计过渡期兼容策略，例如旧路径保留指针或在一个版本窗口内同时支持旧、新入口。
5. 在独立分支分阶段迁移，并为复制 `project/` 的最小可用性增加 smoke 验证。
6. 在模板仓验证通过后，才评估派生仓同步与文档回写策略。

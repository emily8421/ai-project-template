# TEMPLATE-UPGRADE：任务路由表「模板维护 / 同步机制」行章节级标注——下行同步场景最小必读集

> 来源：LUMEN_demo_T2.1（emily8421/LUMEN-DEMO）派生项目回流
> 状态：本地草案，待用户确认后按 `ai/commands/submit-proposal.md` 跨仓提交（2026-11-02）
> 证据积累：hotspot SUMMARY 阶段 N 留观条款「复发 ≥3 次再转提案」——本场景第 3 次复发触发（2026-09-16 / 10-29 / 11-02 三次下行同步任务实测）

## 1. 动机（去项目化）

派生项目执行 `/run sync-methodology`（模板下行同步）时，`ai/index.md` 任务路由表「模板维护 / 规则改造 / 同步机制」行要求读取**完整规则回退包**（7 文件）+ `MAINTAINERS.md` / `CONTRIBUTING.md` / `template-sync.json`。对纯下行同步场景，该读取面存在三重冗余：

1. **与同步跨度无关的固定成本**：单 MINOR / PATCH 小同步（delta 常为个位数文件）与跨多版本大同步的规则读取成本完全相同；某派生项目三次实测中，最小一次同步仅 12 delta，仍整读回退包约 2.5 万字级。
2. **清单内文件在派生仓缺位**：`MAINTAINERS.md` 自模板 v1.70.0 起不下行，普通派生仓并无此文件——路由行清单与派生仓实况脱节。
3. **大半回退包与同步动作无判定交点**：`document-lifecycle-rules.md`（生成 / 审计 docs 才用）、`implementation-lifecycle-rules.md`（编码 / Sprint 才用，仅 §7.1 版本回写语义在同步跨度 adoption 时间接相关）在纯同步任务中无读取必要性；实际执行中同步任务真正依赖的是 SOP 链（`12-sync-template` + `git-guide §5` + 报告模板 + `template-sync.json`）与 `session-rules` 的 Checkpoint / 跨仓角色声明节。

**实测成本曲线**（同一路由行三次复发，逐次抬升）：约 2.5 万字 → ~3 万 token 级 → ~3.5 万 token 级（10 份大文件整读）。同步是派生仓的高频例行任务（每模板发版一次），固定成本随模板规则文件膨胀而线性增长。

**反驳「保守整读有兜底价值」的既有疑虑**（来自第一次复发时的单条记录）：兜底价值与同步跨度无关——同步任务的风险控制实际由预检两阶段契约（A/B 分域、失败即停）、dry-run 边界 grep、`check-derived-sync` 边界校验与「同步后 §3.2 定向重读被改写规则文件」承担，与回退包整读无判定交点。同步确实会改写 `ai/` 规则文件（§3.2 复用张力真实存在），但正解是**同步后对被改写规则做 diff 定向重读**（实测两轮有效），而非同步前整读一遍与本轮动作无关的规则全文。

## 2. 拟改（old → new 建议）

`ai/index.md` 任务路由表「模板维护 / 规则改造 / 同步机制」行，按场景拆分必读集：

**改前**：

> | 模板维护 / 规则改造 / 同步机制 | 修改 `ai/` 规则、入口镜像、同步清单、自检脚本、模板发布 | 完整规则回退包、`MAINTAINERS.md`、`CONTRIBUTING.md`、`template-sync.json`、相关脚本 |

**改后**（章节级标注语义沿用本路由表既有脚注）：

> | 模板维护 / 规则改造 / 同步机制 | 修改 `ai/` 规则、入口镜像、同步清单、自检脚本、模板发布 | **规则改造 / 自检脚本 / 模板发布**：完整规则回退包、`CONTRIBUTING.md`、`template-sync.json`、相关脚本；**派生项目下行同步**：`ai/prompts/maintainers/12-sync-template.md`（全文）、`git-guide.md §5`、`ai/session-rules.md §3.3 / §3.4`、`ai/rules-core.md`（全文，硬规则门禁）；留痕时读 `template-docs/templates/derived-sync-report-template.md`；同步提交后按 `session-rules §3.2` 对**本次被同步改写的规则文件做 diff 定向重读**（替代同步前整读回退包） |

配套约束（写进 `12-sync-template.md` 使用前准备或 `git-guide §5.1`，一句话）：

- 若同步跨度引入的规则变更与派生仓后续动作相关（如同步清单位置、`project-rules` 骨架项），SOP 既有步骤已覆盖核对义务，不因缩小同步前读取面而新增缺口。
- 模板仓会话（维护者侧）不受本标注影响，仍走完整回退包。

## 3. 影响面与版本判断

- **影响文件**：`ai/index.md`（路由表一行）+ `git-guide.md`（§5 或 §5.1 一句配套约束）；`check-template.sh` 既有断言核验建议：路由表含 `implementation-lifecycle` / `commands README` 字样的断言（`:1340/:1341`）针对其他行不受影响；若存在断言要求该行含「完整规则回退包」字样需同步调整（v1.75.8 #491 已有同款断言核验先例）。
- **行为变化**：仅读取面收窄；同步 SOP 全部硬门禁（预检契约 / 失败即停 / dry-run 边界核验 / `check-derived-sync` / A13 矩阵 / 收尾门禁）零改动。
- **版本判断建议**：PATCH（纯文档指引与读取面调整，不新增下游采用面 / 不改同步清单；#491 同款先例为 PATCH）。若维护者认为路由语义变化属规则行为变化，可定 MINOR，由维护者裁决。
- **验证方式**：①`scripts/check-template.sh` 路由表相关断言核验（`ai/index.md` 需含的文件名字样清单按改后行调整，#491 先例）；②改后行的人工核对——「派生项目下行同步」场景按最小集读取即可完成一次真实同步全链（预检 → dry-run → commit → `check-derived-sync` → A13 矩阵零缺口）；③回退兜底演练——规则改造 / 发布类任务按整读路径执行不受影响。
- **风险与兜底**：读取面收窄后，若同步跨度触及其它规则域（如 #490 案例触 `implementation-lifecycle §7.1`），定向重读兜底；`rules-core §2` 不可跳过硬规则（写入确认 / Checkpoint Mode / 失败即停）不依赖回退包整读。极端不确定时 `rules-core §3`「不确定即读完整回退包」兜底条款原样保留。

## 4. 与既有规则的关系（去重）

- **#441 章节级标注（v1.73.0）**：本提案是其同款机制在「模板维护 / 同步机制」行的扩展；#441 已覆盖「回流 / 提案评估」「评估 / 回测」场景，本提案补同步场景（该行无标注是 #441 初扫时「同步侧留观 ≥3 次」条款的兑现对象）。
- **#491 路由行最小必读集（v1.75.8）**：先例同构——「PR / CI / Git 收尾」行已按权威入口分诊收窄，本提案为「模板维护 / 同步机制」行做同款处理；「同模式排查其余路由行」在该轮初扫未做，本提案即其延续。
- **#485 评审总纲（v1.76.0）**：无交集（评审触发矩阵不改路由读取面）。

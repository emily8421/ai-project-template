# TEMPLATE-UPGRADE：规则路由粒度分层（rule routing granularity，按任务形态收窄必读集）

## 1. 动机（去项目化）

模板的规则路由体系已解决「读哪些文件」（`ai/index.md` 路由表）与「不预读全模板」（`ai/rules-core.md` §4），但路由条目的粒度是**整文件**。来源项目跨三个 rollup 阶段累计 11+ 实例表明：相当一部分任务类型对规则的引用面集中于少数章节，整文件加载构成该类任务的主要上下文成本：

1. **提案起草 / 回流评估类**：按「文档任务」路由整读 4 份大规则（约 1370 行），实际高相关仅 2-4 个章节（通用规则 §9/§10、文档生命周期 §2 与 §7.1 状态词典、命令文件全文）——其中一份规则约 450 行与任务无关，估算可省 ~40% 规则读取。
2. **分析 / 评估 / 回测类**：规范基线全文读入、实际仅引用 2 个章节（如 doc-standards 的 03 §3/§4、09 §3/§4）。
3. **同会话续接升级类**：快速续接 → 分析任务升级后，同一规则文件同会话二次整读（`ai/session-rules.md` §3.2 复用边界实际已允许复用，但路由入口未接入该条款）。
4. **工具脚本类**：一次性 `.tmp` 诊断 / 验证脚本走了完整编码任务路由。

**体系内已存在两种粒度形态且不一致**：路由表是整文件粒度；而命令文件已示范章节级窄必读集——`ai/commands/submit-proposal.md` 必读文件仅 3 项且引用到章节级（`ai/global-rules.md` §9）。模板等于已经验证了窄必读集可用，只是没有把它反哺到路由表。

**缺口（本提案补）**：路由表从「整文件必读」升级为「支持章节级标注」，并把同会话复用条款接到路由入口，不改路由门禁本身。

## 1.1 与既有规则的关系（去重）

| 既有规则 | 关系类型 | 说明 |
|---|---|---|
| `ai/index.md` 任务路由表 | **直接增强对象** | 表结构与任务包划分原样保留；仅在必读规则包的文件引用上增加可选章节级标注（本提案 §2.2） |
| `ai/rules-core.md` §3「不确定是否需要某个大规则文件时，先读该文件目录 / 相关章节」 | **升格既有启发式** | 该句已隐含「按章节读合规」，本提案把它从「不确定时的兜底启发」升格为「路由表显式标注的常规选项」，互为表里不冲突 |
| `ai/rules-core.md` §4（按任务所属层只读必读文件，不预读全模板） | **同向，粒度递进** | §4 管「不跨层预读」（文件级），本提案管「层内按章节收窄」（章节级），互补不重复 |
| `ai/session-rules.md` §3.2（同会话规则复用边界） | **接入口** | §3.2 已定义复用条件；本提案在路由表 / rules-core 侧加指针，使「快速续接 → 任务升级」场景不再二次整读，不改动 §3.2 本体 |
| `ai/session-rules.md` §3.1（快速续接最小读取范围） | **先例佐证** | 快速续接模式已是「按场景定义最小读取」的落地先例；本提案把同一思路推广到分析 / 提案类任务 |
| 完整规则回退包（`ai/rules-core.md` §1.4） | **不动，兜底保留** | 「任务类型不明确 / 规则覆盖不足 / 不确定时读完整回退包」原样保留——本提案只作用于「能明确判断任务类型且该任务包存在标注」的场景 |
| `ai/rules-core.md`「不得为了省上下文跳过可能相关的硬规则」 | **安全线，不削弱** | 章节标注只收窄「已证明引用面集中」的任务类型；无标注任务默认整文件，行为不变 |
| #423（跨 Shell 路径预检与失败域隔离，已落地） | **对象不同** | #423 管 shell 命令预检；本提案管规则读取粒度，无重叠 |

## 2. 拟改（核心交付）

### 2.1 落地位置建议

- **`ai/index.md` 路由表**：必读规则包列支持章节级标注 + 表脚注一条（标注语义，见 §2.2）。
- **`ai/rules-core.md` §3**：现有「先读该文件目录 / 相关章节」句后加半句指针——路由表已标注章节的，按标注读取即为合规读取。
- **不新增脚本 / CI 断言**：「引用面是否集中」是语义判断，无法机械化——与六问、观察日志、任务卡执行记录同一力度判断。

### 2.2 机制（三条）

1. **章节级标注语义**：路由表条目内的规则文件引用可选标注章节（写法如 `ai/document-lifecycle-rules.md` §2 / §7.1）。**未标注 = 整文件（现状默认，行为不变）**；标注即授权按所列章节读取；任务需要标注外内容时按现状读全文——保守方向兜底。
2. **首批标注建议**（供维护者 triage 采纳或调整，均来自 §1 实证）：
   - 提案起草 / 回流评估类：`ai/global-rules.md` §9 / §10（`submit-proposal.md` 已如此示范）、`ai/document-lifecycle-rules.md` §2 / §7.1；
   - 分析 / 评估 / 回测类：`ai/doc-standards/03-prd.md` §3 / §4、`ai/doc-standards/09-verification.md` §3 / §4；
   - 同会话续接升级：路由表通用注记「本会话已按规则路由读取且未变更的规则，按 `ai/session-rules.md` §3.2 复用，不重复整读」。
3. **稳定锚点前提**：章节标注依赖既有「章节编号是稳定锚点」条款（`ai/global-rules.md` §5 文档编号规范）——规则文件章节改编号须全量迁移引用，路由表标注随之更新，不新增独立维护机制。

### 2.3 力度

**建议 + 默认**：标注是否存在由模板维护者按实证逐步添加；派生项目可按标注执行，也可保守整读（不算违规）；无标注场景行为与现状完全一致。零 CI 断言。

## 3. 版本影响

建议 **MINOR**：`ai/index.md` 表脚注 + 若干条目标注 + `ai/rules-core.md` 半句指针；不改路由门禁、不改回退包、不加 CI 断言，无标注场景行为零变化。

## 4. 影响面

- 修改：`ai/index.md` ×1（脚注 + 条目标注）、`ai/rules-core.md` ×1（§3 半句）。
- 对派生项目：分析 / 提案 / 回测类任务的规则读取成本下降（按来源项目实测区间约 30~40%）；其余任务无感。
- 不新增需求 / 表 / 接口 / 验收目标，不新增工具链依赖。

## 5. 验证方式（来源项目实证摘要）

- **重复热点实证**：token hotspot 观察日志三个 rollup 阶段累计 11+ 实例同源命中，其中 3 份已提炼入库（阶段 K）——「评估 / 回测 / 提案起草」三类任务均出现「整文件读入、单章节以下实际引用」。
- **量化区间**：提案起草类任务整读 4 大规则约 1370 行、高相关约 3-4 章节，估算可省约 40% 规则读取；同会话二次整读场景可省一整份规则文件（数百行）。
- **体系内先例**：`ai/commands/submit-proposal.md` 必读文件仅 3 项且引用到章节级、`ai/session-rules.md` §3.1 快速续接最小读取——两种「窄必读集」形态已在模板体系内运行，本提案仅将同一形态反哺路由表。
- **未提交**：无脚本 / CI 改动；纯规则文本。

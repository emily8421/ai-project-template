# UI Knowledge（Web UI/UX 设计知识核心层）

> Sync notice: This file is maintained by `ai-project-template` and may be overwritten when a derived project syncs template methodology.
> Do not edit it directly in derived projects; propose reusable changes in `_governance/_proposals/` and upstream them to the template repository.

> 定位：母模板内的轻量设计知识核心层。它保存 Web UI/UX 的方法、记录模型、少量精选模式和来源索引，供派生项目做前端参考分析时按 scope 查询。它不是设计素材下载器，不是截图仓，不是第三方资料镜像，也不替代项目自己的 `frontend-ui-reference-analysis`、前端交互设计或验收记录。

本目录是「UI 探索 → 交付」流水线（`ai/document-lifecycle-rules.md` §5.2.1）中「前端参考分析」阶段的知识来源层。流水线阶段与晋级 Gate（`UI-G-001` ~ `UI-G-007`）已在该文件定义；本目录只补**可查询的设计知识**和**选择规则**，不新增阶段或 Gate。

## 1. 能力定位与边界

**要解决的核心空白**：现有流水线回答了「何时探索、怎样写原型、如何进入实现和验收」，但没回答「可复用设计依据从哪里来、可信度如何、怎样选进当前项目」。本层补这个中间层：

```text
公开来源
  → 来源登记与许可检查
  → 原则 / 模式 / 案例抽取
  → 证据分级与适用边界
  → 当前项目选择 / 排除
  → reference analysis
  → 探索原型 / 正式交互设计
```

**适用**：构思、设计或实现 Web UI 的项目成员；需要基于公开案例生成原型建议的 AI；维护设计知识来源与质量的模板维护者。

**非目标**：

- 不为单个项目定制母模板内容；项目采纳决定只写进项目自己的参考分析。
- 不替代用户研究、可用性测试、设计评审或人工确认。
- 不把公开产品表现推断成其内部设计原则或研究结论。
- 不整库复制第三方 Markdown、截图、设计稿、字体、图标或品牌资产。
- 不将灵感案例直接升级为需求、接口、任务或验收事实。
- 不要求所有 UI 任务加载完整知识目录；必须按任务类型和 scope 选取。

## 2. 知识模型

### 2.1 五类记录

| 记录类型 | ID 前缀 | 用途 | 能否直接作为项目决定 |
|---|---|---|---|
| Source | `SRC-*` | 登记规范、设计系统、研究文章、产品案例或代码来源 | 否，只证明来源存在 |
| Principle | `PRN-*` | 跨产品成立的设计原则及其证据边界 | 需结合项目约束后确认 |
| Pattern | `PAT-VIS-*` / `PAT-INT-*` | 对特定问题可复用的视觉或交互解法 | 需检查适用 / 不适用条件 |
| Case | `CASE-*` | 某个真实产品或设计稿的观察记录 | 否，只用于启发或比较 |
| Recipe | `REC-*` | 按产品类型组织的选型结论与推荐组合（组件库、令牌配置、布局范式、关键页骨架、反模式清单） | 作为比选起点，不替代项目自身核对 |

项目中的「采纳决定」**不回写**核心知识记录，而写入项目自己的 `docs/research/*frontend-ui-reference-analysis.md`。通用知识与项目事实物理分离。

### 2.2 证据等级

| 等级 | 定义 | 使用方式 |
|---|---|---|
| A | 正式标准、规范或平台级权威要求（如 W3C WAI-ARIA、WCAG） | 可作为基线约束，仍需核对适用版本和范围 |
| B | 公共服务设计体系、成熟设计系统或有明确研究依据的指南（如 GOV.UK、USWDS） | 可作为推荐依据，需说明适用场景 |
| C | 可观察的成熟产品模式、开源实现或多案例一致做法 | 可作为候选模式，必须结合项目验证 |
| D | 概念稿、视觉合集、单一案例或来源不完整的灵感（如 `awesome-design-md` 多数条目） | 只能用于发散，不得表述为成熟交互经验 |

证据等级表示「该来源能支撑多强的结论」，不表示视觉质量高低。

## 3. 知识维度

模式按以下十个维度归类，一个模式可关联多个维度：

| 维度 | 解决的问题 |
|---|---|
| 产品与用户任务 | 用户为什么来、怎样完成目标 |
| 信息架构与导航 | 信息如何组织、用户如何定位 |
| 交互流程 | 操作怎样开始、推进和结束 |
| 状态、反馈与恢复 | 系统变化和失败怎样被理解 |
| 视觉与布局 | 内容怎样被扫描和区分 |
| 组件与表单行为 | 控件在不同条件下怎样工作 |
| 内容设计 | 界面文字怎样支持决策 |
| 可访问性与包容性 | 不同能力和输入方式能否使用 |
| 响应式、动效与感知性能 | 设备和等待如何影响体验 |
| 信任、数据与人机协作 | 系统建议和风险如何可理解 |

## 4. 记录字段规范

### 4.1 Source 记录（见 `source-registry.md`）

| 字段 | 说明 |
|---|---|
| SRC-ID | 稳定编号，如 `SRC-A11Y-001` |
| 类型与维度 | 规范 / 设计系统 / 研究 / 产品案例 / 代码；对应 §3 维度 |
| 标题与发布方 | 原始标题、维护机构 |
| 来源 URL | 可核验的权威链接 |
| 证据范围 | 该来源能支撑的证据等级上限（A/B/C/D） |
| 许可与保存策略 | 可保存摘要 / 可保存代码 / 只保存链接 / 待确认 |
| 最后核验 | 日期 + 核验范围 |
| 链接核验状态 | 已核验：可访问 / 暂时不可用（独立于生命周期） |
| 状态 | candidate / reviewed / core / deprecated / retired |

### 4.2 Pattern / Principle 记录（见 `visual-patterns.md` / `interaction-patterns.md`）

| 字段 | 说明 |
|---|---|
| ID | `PAT-VIS-NNN` / `PAT-INT-NNN` / `PRN-NNN` |
| 类型与维度 | Pattern / Principle；对应 §3 维度 |
| 要解决的问题 | 不以风格名代替问题定义 |
| 建议 | 可操作的原则或模式摘要 |
| 适用条件 | 产品类型、用户任务、设备、输入方式、风险等级 |
| 不适用条件 | 常见误用、反例和禁止套用场景 |
| 行为契约 | 触发、状态变化、反馈、恢复、键盘 / 焦点；纯视觉项标不适用 |
| 视觉信号 | 层级、密度、布局、色彩或组件表现；纯行为项标不适用 |
| 来源 | `SRC-ID` + 原始 URL |
| 证据等级 | A / B / C / D |
| 状态 | candidate / reviewed / core / deprecated / retired |

### 4.3 Recipe 记录（配方）

| 字段 | 说明 |
|---|---|
| REC-ID | 稳定编号，按产品类型分段，如 `REC-CS-001`（客服类） |
| 类型与维度 | Recipe；对应 §3 维度（可多个） |
| 适用范围 | 产品类型、端（双端 / 单端）、阶段（Demo / MVP / 产品） |
| 推荐内容 | 选型对比矩阵与推荐组合；每项挂 `SRC-*` / `PAT-*` / `CASE-*` 证据 ID |
| 适用 / 不适用条件 | 同 §4.2 Pattern 口径 |
| 证据等级 | A / B / C / D；整体等级不超过所引证据中的最高等级 |
| 状态 | candidate / reviewed / core / deprecated / retired（沿用 §9 生命周期，不另立） |
| 最后核验 | 日期 + 核验范围 |

使用边界：配方是有证据的推荐起点，不是标准答案；项目仍须在参考分析中做采纳 / 调整 / 排除；所引证据升级、降级或选型环境变化时，配方随之复评。

条目承载：核心层暂不存放 REC 条目；条目由项目族群自建收集层仓库按 §9.1 回流口径承接，达上浮条件后经 `ai/global-rules.md` §9 提案通道升入核心层。

web 形态选型的项目侧声明与核查口径见 `template-docs/profiles/web-fullstack-profile.md` §10。

## 5. 选择流程（按 scope 读取）

AI 做参考分析时**不加载全部知识**，按 scope 选取：

1. 从 UI brief / 输入材料确定：产品类型、用户任务、页面类型、设备范围、关键状态。
2. 按 scope 命中相关维度（§3）和模式文件（visual / interaction）。
3. 只读取命中记录，每条核对适用 / 不适用条件。
4. 输出证据分级 + 采纳 / 调整 / 排除矩阵（见 `template-docs/templates/frontend-ui-reference-analysis-template.md`）。
5. 视觉案例（D 级）只作发散，不得推导为成熟交互结论。

简单页面或无参考输入时，可在参考分析或上游文档中写明豁免理由，不做长分析。

## 6. 原型输入包契约

参考分析的产出是一份「项目参考依据包」，作为探索原型和正式交互设计的输入。最小输入契约（去项目化）：

| 字段 | 说明 |
|---|---|
| 当前界面与任务类型 | 待设计的页面 / 流程与用户目标 |
| 选中的原则 / 视觉模式 / 交互模式 | 引用 `PRN-*` / `PAT-*` ID |
| 每项来源与证据等级 | `SRC-*` + A / B / C / D |
| 适用与不适用条件 | 引用模式字段或按项目改写 |
| 采纳 / 调整 / 排除决定 | 项目级判断，附理由 |
| 必须覆盖的状态 / 恢复 / 可访问性 / 响应式 | 不能只覆盖颜色与布局 |
| 回填位置 | UI brief / 原型 / experience brief / 正式设计 |

落盘路径：`docs/research/YYYY-MM-DD-frontend-ui-reference-analysis.md`（与 `ai/document-lifecycle-rules.md` §5.2.1 一致）。

## 7. 来源策略与版权落盘规则

- 默认只落盘来源元数据、自有摘要、抽象后的原则 / 模式和必要链接。
- 第三方截图、设计稿、字体、图标、品牌素材和大段原文**不进入模板仓**。
- 仓库级开源许可证不自动覆盖其中引用的第三方网站素材；需按资产级权利判断。
- 允许保存代码片段时仍记录许可证、出处和 NOTICE 条件。
- 来源无法确认许可、链接失效或内容无法复核时，链接核验状态记为「暂时不可用」；这不等同于生命周期状态变更。
- 仅依赖「暂时不可用」来源的 Pattern / Principle 必须降为 `candidate`，不得保持 `reviewed` 或 `core`。
- 对公开产品的观察写成「观察到的界面表现」，不得推断为产品团队已验证的内部结论。

首批来源组合见 `source-registry.md`（W3C WAI-ARIA APG / GOV.UK Design System / USWDS / Microsoft HAX Toolkit / awesome-design-md 视觉种子）。

## 8. 许可状态机

每条记录的许可与保存策略按以下状态流转：

```text
待确认 → 可保存摘要 → 可保存代码（附许可证 + NOTICE） → 只保存链接
                       ↑ 来源许可收紧或失效时降级 ←
```

- 升级（摘要 → 代码）必须有明确的资产级许可证据。
- 来源许可变更、链接失效或内容下架时，降级为「只保存链接」或标 retired。
- 许可策略或链接可用性变化记录在 Source 记录的「最后核验」与「链接核验状态」字段。

## 9. 维护与评审升级路径

记录生命周期：`candidate → reviewed → core → deprecated → retired`。

| 状态 | 含义 | 进入条件 |
|---|---|---|
| candidate | AI 起草或新登记，未经人工评审 | 首批默认状态 |
| reviewed | 经维护者逐条人工评审，来源与证据已核验 | 维护者确认所引来源可访问、证据等级准确、适用边界合理 |
| core | 跨 ≥2 项目验证稳定，进入推荐核心集 | 有项目实证 + 评审通过 |
| deprecated | 不再推荐但保留可追溯 | 有更好替代或来源失效 |
| retired | 移出核心，仅留链接 | 内容过时或被替代 |

**首批说明（v1.62.0；Batch 2A 于 2026-08-14 复核）**：首批 13 条模式中 11 条经维护者逐条评审保持 `reviewed`（2026-08-13，PR #348）；`PAT-VIS-004`（D 级视觉启发）维持 `candidate`；`PAT-INT-006` 的唯一来源 Microsoft HAX Toolkit 暂时不可用，降为 `candidate`，待链接恢复并复核后再评审。6 条来源（Source）生命周期仍为 `candidate`；其中 5 条链接已核验可访问，Microsoft HAX Toolkit 标为暂时不可用。core 晋升（需跨 ≥2 项目实证）、证据升级 / 降级、重复模式合并和链接失效检查属 Batch 2（质量治理）。

### 9.1 两仓分工与项目回流

两层分工：母模板核心层（本目录，字段规范与推荐核心，随同步到达各派生项目）；项目族群自建的收集层仓库（承接全部收集量与候选池；建不建、建在哪里由项目族群自行决定，不在模板同步范围）。母模板只约定三件事：ID 与字段规范、回流内容与方式、上浮条件。

项目回流三件事：

- **回流内容**：项目设计实践中产生的观察——选型比选、令牌配置、模式实证、问题与规避——写成 Case（或 Pattern / Recipe 候选）交收集层仓库，按其收集 SOP 入库；
- **回流边界**：项目设计稿与品牌资产不入库；采纳 / 排除决定仍写在项目自己的参考分析（§2.1），不回写知识记录；
- **上浮通道**：候选记录在 ≥2 个项目实证后，由项目按 `ai/global-rules.md` §9 既有通道起草 TEMPLATE-UPGRADE 提案升入核心层。此为 core 进入条件（「有项目实证」）的操作说明，不改变晋升标准本身。

维护分期：

| Phase | 目标 |
|---|---|
| Phase 0 | 建核心层 schema + 来源索引 + 少量精选模式（本版） |
| Phase 1 | 双项目试点验证 schema 跨场景可用（Batch 0 已完成） |
| Phase 2 | 基于真实项目反馈扩充模式 + 建人工评审节奏（Batch 2） |
| Phase 3 | 评估是否独立 Web 领域模板或独立知识仓（Batch 3，需独立提案） |

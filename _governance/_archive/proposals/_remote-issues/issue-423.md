# TEMPLATE-UPGRADE: 跨 Shell 命令预检与失败域隔离

> 来源：LUMEN_demo_T2.1（emily8421/LUMEN-DEMO）派生项目回流。
> 去项目化说明：本文提炼自 AI 在不同 shell 中执行无副作用文件定位与读取时的兼容性问题，不包含项目业务、客户数据、私有路径或运行环境凭据。
> Release impact：none（提案草案；若模板采纳，建议 PATCH）。
> Release strategy：同主题聚合或由维护者单独发布。

## 1. 动机（去项目化）

模板规则已要求命令失败立即停止，并要求预检使用精确查询和失败域隔离。但在 Windows PowerShell、Bash 等 shell 间，文件通配、路径字面量和多个读取动作的失败传播不同：

- 某些 shell 会展开路径通配，另一些会将其作为字面文件名；
- 将多个独立读取串为一个命令时，一个不存在的辅助路径会使整批退出为非零；
- AI 若未先确认实际路径，容易把目录约定误当作仓库事实，造成无副作用的预检中断。

### 1.1 Codex CLI 工具批处理补充（2026-09-01）

派生项目在 Codex CLI 中多次复现另一种同类失败传播：将多个独立只读命令交给同一工具批处理时，任一子命令的预期性非零退出（例如无匹配或可选路径缺失）会被外层聚合为整批失败。若 AI 只按聚合退出码裁决，会丢失同批已经取得的 Git、版本或文件读取事实，并把本应标记为 `not-found` / `no-match` 的结果误报成需要重新授权的任务阻塞。

这不是放宽“失败即停”：预期性只读结果应在命令设计时被独立建模，避免进入失败路径；真正的命令、权限、sandbox、网络、超时、写入、构建、测试、CI 和远端失败仍必须立即停止。该现象虽由 Codex CLI 集中触发，规则措辞应保持工具无关，以同样约束其他会聚合子命令状态的 AI 工具。

这类问题不应放宽构建、测试、权限、网络或远端操作的停止纪律；目标是让文件定位阶段先取得可靠事实，避免可预防的 shell 兼容性错误。

## 1.2 与既有规则的关系（去重）

- `ai/rules-core.md` §4“预检精确查询与失败域隔离”：已规定精确查询、关键事实与辅助检查分批、同一失败点不自动重试。本提案补充跨 shell 的可执行路径预检方式和“不同定位查询”的边界，属于机制细化，互补不重复。
- `ai/rules-core.md` §4“命令失败、超时、权限不足、sandbox / network 错误或 CI pending 时先停止”：该规则保障任务失败可见。本提案不改变其适用范围，只要求在无副作用的路径定位前避免产生可预防的失败。
- `TEMPLATE-UPGRADE-windows-utf8-rule-reading.md`（已归档）：处理中文 Markdown 的输出编码和重读，不处理路径通配、命令批次失败传播或 shell 语义；环境相邻、对象不同。
- `TEMPLATE-UPGRADE-submit-proposal-gh-robustness.md`（已归档）：处理跨仓 `gh` 命令的认证、标签与 Markdown 参数稳健性；本提案处理本地文件定位，层级和机制不同。

## 2. 拟改

建议在模板的通用执行规则中增加“跨 shell 路径预检”小节，并在命令编写约定中引用：

1. 命令示例标明适用 shell。涉及路径通配时，不假设 Bash 的 glob 展开在 PowerShell 或其他宿主中成立。
2. 对有限、预期存在的文件，先用无副作用的精确定位或存在性探测确认路径；读取时使用 shell 对应的字面路径 API，例如 PowerShell 的 `Get-Content -LiteralPath`。
3. 多个彼此独立的辅助读取按失败域拆分。一个路径未命中不得掩盖已取得的 Git、版本或其他独立事实。
4. 若无副作用的路径解析 / 路径假设失败，AI 应先报告该失败；允许执行**一次不同的只读定位查询**以获得准确路径。该查询不是对原命令的自动重试，且不得在完成定位前进入写入、构建、安装、远端或其他状态变更步骤。
5. 构建、测试、lint、迁移、权限、sandbox、网络、CI、远端操作和任何可能改变状态的命令失败，仍严格按既有规则立即停止；本例外不适用。
6. 对工具批处理中的独立只读结果，逐项保留 `pass` / `fail` / `not-found` / `no-match` / `not-checked`；不得以外层 all-or-nothing 聚合结果覆盖已确认事实。预期性 `not-found` / `no-match` 不属于任务阻塞，也不应触发新的写入确认或重新授权。
7. Codex CLI 等会聚合子命令状态的工具，应避免将可能返回预期性非零退出的辅助检查与关键事实读取放进同一批；无法拆分时，必须在工具侧用结构化结果显式区分预期性结果与真实失败。

## 4. 影响面与风险

- 影响面：模板规则入口、命令文档作者和使用 Windows PowerShell 的派生项目；Bash / macOS / Linux 同样受益于明确 shell 前提。
- 兼容性：不新增依赖、不调整同步清单、不要求既有派生项目迁移；下行同步后自然生效。
- 风险：若“辅助错误”定义过宽，可能被误用来绕过失败即停。缓解方式是将例外限定为无副作用的路径定位，并排除构建、测试、网络、权限、CI、远端和任何写入。
- 工具适配风险：若只按外层批处理退出码裁决，预期性只读结果会被误判为任务失败。缓解方式是逐项输出状态，并禁止用 all-or-nothing 聚合掩盖独立事实。
- 非目标：不要求每个命令都自动探测所有路径；不改变任务事实的裁决优先级；不将路径错误静默吞掉。

## 5. 验证方式与验收标准

模板落地后，至少验证：

1. PowerShell 下通过精确探测加 `-LiteralPath` 读取已知文件，不依赖 `Get-Content` 的路径通配行为。
2. Bash 与 PowerShell 的命令示例均能清楚表达路径前提或定位步骤。
3. 一个可选辅助路径不存在时，关键只读事实仍单独报告；AI 仅可执行一次不同的只读定位查询，不进入状态变更。
4. 构建、测试、权限、网络或远端命令失败时，流程仍立即停止，不触发本提案的兼容性例外。
5. 模板自检、至少一个 Bash 派生项目与一个 PowerShell 派生项目的最小命令演练通过。
6. 在会聚合子命令状态的工具中，包含一个 `no-match` 或可选路径缺失的批次仍能保留其它独立只读事实，并将该项按语义标记，而不产生任务阻塞。

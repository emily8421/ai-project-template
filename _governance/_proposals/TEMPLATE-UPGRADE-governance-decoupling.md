# TEMPLATE-UPGRADE：治理机制解耦管理（机制生命周期 + 域间契约 + 载体演进路线）

> 来源：模板维护者（2026-10-29 治理体系全面评估会话；维护者提出五域解耦管理诉求：文档体系管理 / 编码实现与验证 / 研发数据链知识沉淀 / 模板自身演进 / 协调层机制管理）
> 状态：待评估（评估报告 + 分阶段解决方案已落盘本提案；Phase 0 待拍板）
> 目标版本：Phase 1 拟 PATCH（待确认）；本提案落盘本身不改 VERSION
> Release impact：none（提案落盘）/ Phase 1 = patch（建议，待维护者确认）
> Release strategy：分阶段——Phase 0 口径拍板 → Phase 1 契约层 PATCH → Phase 2 首轮机制审计 → Phase 3 载体层实证评估 → Phase 4 常态运转

## 1. 动机与背景

模板治理机制持续累积：14 类机制（`MECH-*`）+ 12 类工具能力（`TOOL-*`）+ 2114 项自检断言 + C1 triage 路由包约 900 行。维护者提出解耦管理诉求，按五域划分：**①基于软件工程规范的文档体系管理、②基于文档体系的编码实现与验证、③研发数据链的知识沉淀与复用管理、④模板自身的演进管理、⑤其上的协调层机制管理**。

本提案回答三个问题：现有体系的解耦程度到底如何；"机制越来越多"的结构性根因是什么；如何分阶段走向更合理的机制与治理体系。

### 1.1 与既有规则 / 提案的关系（去重）

- **governance-handbook-agent-tool-registry 提案**（`_proposals/TEMPLATE-UPGRADE-governance-handbook-agent-tool-registry.md`，Batch 1-2 已落地 v1.61.6/v1.65.1，Batch 3-5 未授权）：**部分吸收 + 新增**。其 Batch 3（五角色契约 / §5.5 交接字段 / §6.5 十条冲突审核）被本提案 Phase 1/2 以轻量方式吸收（不建 Agent、不并发、不拆文件）；其 §8.1 Knowledge 显式影响域与本提案域划分一致；**机制生命周期通道（状态 / 退役 / 审计节奏）为本提案新增，原提案没有**。载体层拆分 = 原提案 Batch 4-5 原样，本提案补明触发条件。
- **capability-packages.md**（机制注册表，v1.61.6）：**承载点**。本提案 Phase 1 的落点即其 §4 表扩列 + §9 维护要求补强，不新建平行注册表。
- **rd-data-chain.md §4**（"无自检门禁、避免过度治理"口径）：**边界对齐**。本提案 Phase 1 只加人读字段与审计节奏，不新增 check-template 硬断言，与该口径一致；`MECH-*` 存在性校验若未来引入，按 GOV-C-007 口径另行评估且默认 advisory。
- **#485 评审机制总纲**（open issue，已拍板留独立会话实施）：**对象不同、互补**。#485 补评审触发钩子（协调层"到点必做什么"），本提案补机制自身的管理框架（"机制怎么进、怎么退、怎么交接"）；#485 落地后其触发矩阵作为协调域机制登记进 MECH 表，走本提案的生命周期管理。
- **TEMPLATE-UPGRADE-domain-layout.md**（已落地 v1.75.0）：**先例参照**。三层布局定型"机制定型先行、迁移待实证（Batch C/D）"的分阶段节奏，本提案同款。
- **domain-template-inheritance 提案**（部分落地）：**指向**。其"没有实证不推进目录级重组"原则被本提案沿用为载体层门槛。

**本提案不重复它们**：现有体系解决了"机制有哪些、谁负责、怎么执行"，尚未解决"机制怎么进出门、域间怎么交接、载体何时拆"——本提案补的是治理的治理（meta-governance）这一层。

## 2. 现状评估（2026-10-29，基于 v1.75.5 实查）

### 2.1 三层解耦程度判定

| 层 | 现状 | 结论 |
|---|---|---|
| **概念层**（谁负责什么） | `capability-packages.md` §3 七分区与维护者五域几乎一一对应（任务协调→协调层；文档→文档体系；实现+测试验收→编码实现与验证；知识记录→研发数据链；模板维护→演进管理；专项说明→横切）；14 条 MECH-* 按分区挂负责人 | **已解耦，维持** |
| **契约层**（域间交接、机制进出） | 跨分区协作只有一句"重新确认"；交接字段仅有未授权草案（governance 提案 §5.5）；**MECH 登记无状态、无退役条件、无审计节奏** | **半成品，Phase 1 补齐** |
| **载体层**（规则文件按域物理分开） | 三处域间混合（见 2.2） | **维持实证门槛，Phase 3 评估** |

### 2.2 载体层三处域间混合（实查证据）

| 载体 | 混合域 | 证据（章节实查） |
|---|---|---|
| `ai/session-rules.md` | 协调域（§1-§3 续接 / checkpoint / 跨仓声明、§5 写入确认、§8 多会话）+ 知识域（§4.1-§4.3 hotspot / rollup / pitfall、§6.1 checkpoint rollup） | 知识沉淀规则寄生在会话协调文件 |
| `ai/implementation-lifecycle-rules.md` | 实现域（§1-§5）+ 验证域（§6-§7）+ 演进域钩子（§7.1 回写职责表管 VERSION/CHANGELOG） | 验证拆分已有立案（GOV-C-004，拍板"试点后拆"） |

### 2.3 风险项摘要（触发侧，详见评估会话报告）

- **A 档（已实证复发的弱触发）**：评审无强触发点（gmbl E2~E5 断档三周，#485 待落地）；规则→执行节点脱钩（#481 已修单点、同型未盘点）；派生会话回写母仓 registry 靠自觉（A13 完成判据矩阵不含 registry 行，LUMEN 4 轮漏登实证）；回流提案引用失真（#478/#485 两案）。
- **B 档（结构性弱触发）**：同步采用清单 advisory 无回收（G2/G4）；hotspot/pitfall 未汇总条目无老化机制；**机制注册表完整性无校验（GOV-C-007 首批人工）**；图表生成端无兜底（#485）。
- **C 档（挂账观察）**：保留分支长期挂账（`change/domain-template-docs-folder` 3 个月）；本地续接文件换机失效（已实证一次）；PATCH 豁免 e2e（合规设计）。

**关键判定：A/B 档根因高度趋同——"有规则、无到点钩子"且钩子无域归属 owner；机制无退役通道使钩子债务只增不减。**

### 2.4 耦合评估结论

- 设计性解耦健康：rules-core 只路由不承载业务、手册不复制规则正文、`_governance/` 不下行、rd-data-chain 防回流反向断言。
- 真实双写点 3 处（均未断言化）：`template-sync.json` ↔ sync-template.sh 兜底 ↔ check-template（三写）；同步口径 git-guide §5 ↔ 12-sync-template（#478/#484 两次成对改）；命令路由 ai/index.md ↔ commands README ↔ prompt 文件。
- 成功先例：VERSION ↔ CHANGELOG ×2 三件套已被 #459 断言机制化——"双写点断言化"路线可行。

## 3. 解决方案（分阶段）

### Phase 0：口径拍板（本提案确认）

- 确认范围：Phase 1 三项（机制生命周期 / 域间交接契约 / 准入判据）+ 可选搭车项（global-rules 域标签）。
- 确认载体层维持"实证后动"口径（Phase 3 触发条件见 §3.3）。
- 版本影响：none。产物：本提案状态更新。

### Phase 1：契约层 PATCH（轻量，零迁移）

| # | 改动 | 落点 |
|---|---|---|
| 1 | MECH 表扩三列：`状态`（candidate/experimental/active/deprecated/retired，与 TOOL-* 同款语义）+ `退役条件` + `最近审计`；首轮为 14 机制登记初始状态（预计全部 active） | `template-docs/capability-packages.md` §4 |
| 2 | 机制审计节奏：半年度（6 月 / 12 月窗口）按十条冲突审核清单（governance 提案 §6.5）审计一次，结论写 `_governance/ai-records/`；孤儿 / 过期机制走退役，退役需迁移消费者 + 更新注册表 + CHANGELOG | `capability-packages.md` §9 + 新增审计节 |
| 3 | 新机制准入四问：归哪个域 / 触发点挂在哪 / 谁验收 / 何时可退役——四问不全不进表 | `capability-packages.md` §9 |
| 4 | 域间交接契约：按五域写「域间交接与 Gate」节（吸收 governance 提案 §5.5 字段：权威输入 / 请求动作 / 允许范围 / 禁止事项 / 完成条件 / 回传证据 / 人工确认）；先本分区后跨分区、跨域修改先列影响清单 | `capability-packages.md` 新节 |
| 5 | （可选搭车）global-rules 各节标域标签（如 `[域：实现]`），不拆文件 | `ai/global-rules.md` 各节标题行 |

- 版本影响：patch（人读治理说明补强，不改默认行为 / 同步清单 / 门禁；符合兼容性默认规则）。
- 验证：全量自检（capability-packages 现有 3 条关键词断言保留）+ `git diff --check` + md-clean 触达面 + CI。
- 明确不做：不新增 check-template 硬断言（rd-data-chain §4 / GOV-C-007 口径）；不建 Agent；不并发；不拆文件。

### Phase 2：首轮机制审计（advisory，不改机制本身）

- 按十条冲突审核清单对 14 机制 + 12 工具跑首轮审计，产出 `_governance/ai-records/` 审计记录：所有权冲突 / 触发冲突 / 孤儿 / 过期 / 验证缺口清单。
- 审计发现的修正（如某机制该降级 / 该退役 / 该补钩子）走后续 PATCH，不在本轮搭车。
- 版本影响：none（审计记录入 ai-records，不递增）。

### Phase 3：载体层实证评估（满足触发条件才立项）

| 拆分候选 | 触发条件（满足任一） | 对应挂起项 |
|---|---|---|
| verification 拆出独立规则文件 | 双用例试点（文档生成 / Sprint 实现验收）实证实现-验收边界冲突或双重权威 | GOV-C-004 / governance 提案 Batch 4 |
| session-rules 拆出知识管理规则 | pitfall/hotspot 流程因寄生协调文件漏触发 ≥2 次 | 新候选（本提案首立） |
| global-rules 域标签 | 不等触发，Phase 1 可选搭车 | — |

- 载体拆分若立项：单独提案 + MINOR（同步清单 / 断言 / 链接迁移，v1.67.0 先例）+ L3 e2e。
- 试点观察指标沿用 governance 提案 Batch 4（是否减少无关读取 / 是否争夺文件 / 交接是否可恢复 / 失败能否归位责任域）。

### Phase 4：常态运转（无需发版）

- 机制生命周期通道进入半年度节奏；退役先例出现后评估 `MECH-*` 存在性 advisory 校验是否重启（GOV-C-007）。
- 双写点断言化三处（sync 清单三写 / 同步口径两处 / 命令路由）按独立窄提案逐个评估，不搭车本提案。
- 上轮评估建议 #1（A13 补 registry 行）/ #4（prompt 11 先期核实句）为独立窄提案，可与其他窗口聚合，不搭车本提案。

# TEMPLATE-UPGRADE: Web UI/UX 设计知识能力与原型参考输入体系

> 来源：模板维护者（2026-08-13 对公开 UI 设计资料与现有 UI Exploration 流程的评估）
> 状态：候选 / 待评估
> 目标版本：待确认；建议先做双项目试点，再按 Batch 发布
> Release impact：none（本次只新增提案，不修改同步范围或模板行为）
> Expected implementation impact：minor（AI 建议；若新增同步目录、参考分析模板并改变 UI 任务推荐流程）
> Release strategy：试点验证后单独发布核心能力；内容扩充按同主题 patch 聚合；大规模语料库延后评估独立 Web 领域层

## 0. 执行摘要

本提案建议把现有 UI 原型流程中缺失的“可复用参考依据”补成模板级能力。目标不是为某个具体项目服务，也不是把一个公开设计目录整体复制进模板，而是让未来 Web 项目能够：

1. 从经过分类、标源和分级的设计知识中选择参考依据。
2. 把通用原则、视觉模式、交互模式和案例启发转换为当前项目的原型输入。
3. 明确哪些内容只是灵感，哪些有规范或研究证据，哪些仍需用户验证。
4. 将采纳与不采纳的判断追溯到 UI brief、参考分析、探索原型、正式交互设计和验收。
5. 持续吸收新的公开资料，同时控制版权、时效、上下文体积和领域污染。

综合建议采用两层结构：

- **母模板内的轻量核心层**：保存方法、记录模型、少量精选模式、来源索引和项目参考分析模板，随模板同步。
- **可扩展语料层**：保存体量大、更新快、领域性强的案例和素材；先作为外部来源或实验仓，达到实证门槛后再决定是否建设 Web 领域模板或独立知识仓。

`VoltAgent/awesome-design-md` 可作为视觉案例的首批种子来源，但不能作为交互设计的主要证据源。某个开发者工具或知识工作台项目可以作为首个试点，但其业务事实、页面结构和技术选择不得写入模板同步文件。

## 1. 动机（去项目化）

### 1.1 当前问题

模板已经具备较完整的 UI Exploration to Delivery Pipeline：

```text
inputs / UI brief
  -> frontend UI reference analysis
  -> UI prototype exploration / visual exploration
  -> frontend experience brief
  -> frontend interaction
  -> UI prototype strategy
  -> 08 implementation
  -> 09 verification
```

其中 `ai/document-lifecycle-rules.md` §5.2.1 已把参考分析定义为正式阶段（文档路径 `docs/research/*frontend-ui-reference-analysis.md`、晋级 Gate `UI-G-001` inputs→reference analysis 与 `UI-G-002` reference analysis→exploration prototype、职责为“抽取参考产品 / 截图 / 视觉偏好中的可借鉴点”），现有命令也会要求 AI 给出成熟产品或设计系统基线。即“要做参考分析”已有阶段与 Gate 约束，但模板目前没有：

- 对应的 `frontend-ui-reference-analysis` **项目级落盘模板文件**（阶段与 Gate 已定义，但 `template-docs/` 下无模板文件）。
- 可按问题、产品类型和证据等级检索的设计知识集合。
- 区分视觉启发、交互模式、规范要求和用户研究证据的统一模型。
- 将通用知识转换为项目原型输入的选择、排除和追溯规则。
- 公开资料的许可、来源、更新时间、失效和扩充治理方式。

结果是每次 UI 任务仍主要依赖 AI 临场记忆、即时搜索或用户零散截图。即使 AI 能推荐成熟产品，也难回答：为什么适用、什么条件下不适用、交互状态是否完整、证据强度如何、应该回填到哪个项目文档。

### 1.2 对 `awesome-design-md` 的评估结论

对本地检出的公开目录做过一次结构和关键词审计，得到以下基线：

- 目录包含 74 份 `DESIGN.md`，适合观察视觉语言、布局、色彩、字体、组件外观和品牌表达。
- 关键词扫描只在约 6/74 文档中发现较明确的任务流描述，用户研究相关内容为 0/74，撤销或恢复相关内容约 2/74。该统计是启发式扫描，不等于逐篇语义评审。
- 根说明宣称的部分预览资产在本地检出中不存在，说明来源完整性和可复现性需要独立校验。
- 文档更接近基于公开站点生成的视觉设计摘要，不应被当作真实产品团队的交互决策、用户研究结论或可用性证据。

因此该目录当前可直接贡献的是“视觉案例候选”和“界面风格词汇”；需要二次抽取后才能进入核心知识层。交互、可访问性、错误恢复、内容设计、研究方法和人机协作等内容必须从其他来源补齐。

### 1.3 本提案要解决的核心空白

本提案补的是“知识到项目设计输入”的中间层：

```text
公开来源
  -> 来源登记与许可检查
  -> 原则 / 模式 / 案例抽取
  -> 证据分级与适用边界
  -> 当前项目选择 / 排除
  -> reference analysis
  -> exploration prototype / formal interaction design
```

它不是设计素材下载器，不是截图仓，也不是另一个原型工具。

## 1.4 与既有规则的关系（去重）

- **UI Exploration to Delivery Pipeline**（`ai/document-lifecycle-rules.md` §5.2.1，已启用）：定义 UI brief、参考分析、探索原型、体验 brief、正式交互设计、实现与验收的顺序和 Gate。**互补不重复**：本提案不改变主链，只补 `reference analysis` 的标准输入、选择规则和可追溯产物。
- **需求探索原型**（`_archive/proposals/TEMPLATE-UPGRADE-ui-prototype-exploration.md`、`ai/commands/ui-prototype-exploration.md`，已实施）：定义早期原型的触发、边界和输出。**机制不同**：它负责运行探索流程；本提案提供流程消费的知识和参考依据，不新建平行原型命令。
- **UI 原型策略**（`_archive/proposals/TEMPLATE-UPGRADE-ui-prototype-strategy.md`、`ai/doc-standards/ui-prototype-strategy.md`，已实施）：定义正式实现前的原型形式、覆盖范围和可视化证据。**层级不同**：它是实现前门禁；本提案发生在更早的参考选择阶段，也可为门禁提供设计理由。
- **前端交互设计**（`_archive/proposals/TEMPLATE-UPGRADE-frontend-interaction-design.md`、`ai/doc-standards/frontend-interaction.md`，已实施）：定义页面流、状态、错误、权限、接口和验收追溯。**互补不重复**：本提案不替代项目交互设计，只提供可引用的模式及适用边界。
- **UI Brief / Experience Brief 模板**（`template-docs/ui-brief-intake-template.md`、`template-docs/frontend-experience-brief-template.md`，已启用）：分别保存输入偏好与用户确认后的体验原则。**指向**：知识库输出先进入参考分析，只有用户确认后的结论才进入 experience brief 或正式设计。
- **复杂 Web 项目 Profile**（`template-docs/web-fullstack-profile.md`，已启用）：定义 App Shell、目录、纵切和验证入口。**对象不同**：它解决代码结构与工程 Gate；本提案解决设计知识、体验依据和原型输入。
- **知识记录机制**（`template-docs/capability-packages.md` 中 `MECH-KNOW-001`，已启用）：定义调研来源、结论和长期事实回写。**合并入**：来源登记和抽取记录复用现有知识治理，不另建平行知识生命周期。
- **领域模板继承提案**（`_proposals/TEMPLATE-UPGRADE-domain-template-inheritance.md`，部分实施）：规定体量大、演进快、领域专属的内容不应无条件进入母模板。**指向**：母模板只承载轻量核心；大规模 Web 案例库是否独立，待双项目试点和规模数据验证。
- **治理手册与知识负责人提案**（`_proposals/TEMPLATE-UPGRADE-governance-handbook-agent-tool-registry.md`，部分实施）：讨论知识记录责任和机制登记。**层级不同**：它管理模板资产和责任边界；本提案定义一个具体的 Web 设计知识能力，不提前创建独立 Agent 或工具注册系统。

**本提案不重复它们**：现有能力已经回答“何时探索、怎样写原型、如何进入实现和验收”，但没有回答“可复用设计依据从哪里来、可信度如何、怎样选进当前项目”。本提案只补这一空白。

## 2. 能力定位与边界

### 2.1 目标用户

- 使用模板构思、设计或实现 Web UI 的项目成员。
- 需要基于公开案例生成原型建议的 AI。
- 维护设计知识来源、抽取结果和质量状态的模板维护者。

### 2.2 目标产出

对项目使用者，最终产出不是“完整知识库副本”，而是一份紧凑的项目参考依据包：

- 当前界面和任务类型。
- 选中的原则、视觉模式和交互模式。
- 每项的来源、证据等级、适用条件和不适用条件。
- 对当前项目的采纳、调整或排除决定。
- 必须覆盖的状态、恢复、可访问性和响应式要求。
- 应回填的 UI brief、原型、experience brief 或正式设计位置。

对模板维护者，产出是可维护的来源登记和精选核心目录，不是第三方资料镜像。

### 2.3 非目标

- 不为单个项目或单个产品定制母模板内容。
- 不替代用户研究、可用性测试、设计评审或人工确认。
- 不把公开产品表现推断成其内部设计原则或研究结论。
- 不整库复制第三方 Markdown、截图、设计稿、字体、图标或品牌资产。
- 不将灵感案例直接升级为需求、接口、任务或验收事实。
- 不在首批引入向量数据库、抓站工具、嵌入流水线或新的常驻 Agent。
- 不要求所有 UI 任务加载完整知识目录；必须按任务类型和 scope 选取。

## 3. 知识范围：除界面和交互外还应覆盖什么

建议用“产品体验设计”而不是狭义“界面图库”作为范围，共分十个维度：

| 维度 | 解决的问题 | 典型内容 |
|---|---|---|
| 产品与用户任务 | 用户为什么来、怎样完成目标 | JTBD、任务优先级、角色和场景边界 |
| 信息架构与导航 | 信息如何组织、用户如何定位 | 层级、搜索、过滤、渐进披露、逃生路径 |
| 交互流程 | 操作怎样开始、推进和结束 | 主流程、分支、批量操作、确认、撤销 |
| 状态、反馈与恢复 | 系统变化和失败怎样被理解 | 加载、空态、错误、冲突、重试、撤销、降级 |
| 视觉与布局 | 内容怎样被扫描和区分 | 密度、层级、排版、色彩、间距、数据展示 |
| 组件与表单行为 | 控件在不同条件下怎样工作 | 校验、默认值、焦点、禁用、组合组件 |
| 内容设计 | 界面文字怎样支持决策 | 标签、帮助、错误文案、风险提示、术语一致性 |
| 可访问性与包容性 | 不同能力和输入方式能否使用 | 键盘、焦点、语义、对比度、读屏、认知负担 |
| 响应式、动效与感知性能 | 设备和等待如何影响体验 | 断点、触控、骨架屏、过渡、减少动态效果 |
| 信任、数据与人机协作 | 系统建议和风险如何可理解 | 隐私、权限、可解释性、AI 确认、人工接管、纠错 |

用户研究与评估方法横跨以上维度，用于判断这些知识是否真的适合当前项目。工程实现约束同样横跨各维度，用于确认模式在当前技术、性能和安全边界内可实现。

## 4. 建议的知识模型

### 4.1 四类记录

| 记录类型 | 用途 | 能否直接作为项目决定 |
|---|---|---|
| Source | 登记规范、设计系统、研究文章、产品案例或代码来源 | 否，只证明来源存在 |
| Principle | 跨产品成立的设计原则及其证据边界 | 需结合项目约束后确认 |
| Pattern | 对特定问题可复用的视觉或交互解法 | 需检查适用 / 不适用条件 |
| Case | 某个真实产品或设计稿的观察记录 | 否，只用于启发或比较 |

项目中的“采纳决定”不回写核心知识记录，而写入项目自己的 `frontend-ui-reference-analysis`。这样可以避免通用知识和项目事实混在一起。

### 4.2 最小字段

每条核心记录至少包含：

| 字段 | 说明 |
|---|---|
| ID | 稳定编号，如 `SRC-A11Y-001`、`PAT-STATE-003` |
| 类型与维度 | Source / Principle / Pattern / Case；对应 §3 维度 |
| 要解决的问题 | 不以风格名代替问题定义 |
| 建议 | 可操作的原则或模式摘要 |
| 适用条件 | 产品类型、用户任务、设备、输入方式、风险等级 |
| 不适用条件 | 常见误用、反例和禁止套用场景 |
| 行为契约 | 触发、状态变化、反馈、恢复、键盘 / 焦点；纯视觉项可标不适用 |
| 视觉信号 | 层级、密度、布局、色彩或组件表现；纯行为项可标不适用 |
| 来源 | Source ID、原始 URL、标题、发布方 |
| 证据等级 | A / B / C / D，见 §4.3 |
| 许可与保存策略 | 可保存摘要 / 可保存代码 / 只保存链接 / 待确认 |
| 最后核验 | 日期、链接状态、是否已过时 |
| 状态 | candidate / reviewed / core / deprecated / retired |

### 4.3 证据等级

| 等级 | 定义 | 使用方式 |
|---|---|---|
| A | 正式标准、规范或平台级权威要求 | 可作为基线约束，但仍需核对适用版本和范围 |
| B | 公共服务设计体系、成熟设计系统或有明确研究依据的指南 | 可作为推荐依据，需说明适用场景 |
| C | 可观察的成熟产品模式、开源实现或多案例一致做法 | 可作为候选模式，必须结合项目验证 |
| D | 概念稿、视觉合集、单一案例或来源不完整的灵感 | 只能用于发散，不得表述为成熟交互经验 |

证据等级表示“该来源能支撑多强的结论”，不表示视觉质量高低。`awesome-design-md` 的多数条目应默认从 D 级案例开始；只有能回到独立规范、源码或研究证据时，相关原则或模式才能提高等级。

## 5. 来源策略与首批候选

### 5.1 来源组合

首批来源不应只依赖产品截图或设计稿，应至少覆盖：

| 来源类型 | 首批候选 | 主要贡献 |
|---|---|---|
| 可访问性规范 | W3C WAI-ARIA Authoring Practices | 组件语义、键盘和焦点行为 |
| 公共服务设计 | GOV.UK Design System / Service Manual | 服务流程、内容、表单、研究和可访问性 |
| 政府设计系统 | U.S. Web Design System | 组件、模式、可访问性和实现边界 |
| 人机协作指南 | Microsoft Human-AI Experience Toolkit | AI 建议、纠错、控制、信任和人工接管 |
| 视觉案例集合 | `VoltAgent/awesome-design-md` | 风格词汇、布局、排版、色彩和视觉案例候选 |
| 成熟产品观察 | 按具体任务补充公开产品与开源实现 | 工作流、信息密度和状态模式候选 |

候选链接必须在实施时重新核验，并记录最后核验日期；本提案只确定来源类型和筛选方向。

### 5.2 版权与落盘规则

- 默认只落盘来源元数据、自有摘要、抽象后的原则 / 模式和必要链接。
- 第三方截图、设计稿、字体、图标、品牌素材和大段原文默认不进入模板仓。
- 仓库级开源许可证不自动覆盖其中引用的第三方网站素材；需要按资产级权利判断。
- 允许保存代码片段时仍应记录许可证、出处和必要的 NOTICE 条件。
- 来源无法确认许可、链接失效或内容无法复核时，记录状态为 candidate / unavailable，不进入 core。
- 对公开产品的观察必须写成“观察到的界面表现”，不得推断为产品团队已验证的内部设计结论。

## 6. 建议的模板形态

### 6.1 母模板轻量核心层

建议首批候选文件如下：

| 文件 | 职责 |
|---|---|
| `template-docs/ui-knowledge/README.md` | 能力定位、知识模型、选择流程、版权和维护规则 |
| `template-docs/ui-knowledge/source-registry.md` | 精选来源、Source ID、证据范围、许可和最后核验时间 |
| `template-docs/ui-knowledge/visual-patterns.md` | 经过抽象的视觉、布局、密度和展示模式 |
| `template-docs/ui-knowledge/interaction-patterns.md` | 流程、状态、反馈、恢复、可访问性和人机协作模式 |
| `template-docs/frontend-ui-reference-analysis-template.md` | 将通用知识转换为项目参考依据包的模板 |

首批使用 Markdown 和稳定 ID，不立即引入 JSON / YAML 双写。只有出现程序化查询、自动校验或规模增长的真实需求后，才评估机器可读权威源和文档生成方式。

### 6.2 项目级参考依据包

派生项目按既有路径生成：

```text
docs/research/YYYY-MM-DD-frontend-ui-reference-analysis.md
```

建议最小结构：

1. UI brief 与问题定义。
2. 当前产品类型、用户任务、设备和约束。
3. 候选知识记录与来源。
4. 采纳 / 调整 / 排除矩阵及理由。
5. 页面、流程、状态、恢复、可访问性和响应式输入。
6. 视觉方向和明确禁区。
7. 冲突、待确认项与需要用户研究验证的假设。
8. `UI-G-002` 判断及下游回填位置。

项目级分析可以引用核心记录 ID，但必须保留当前项目的决定和确认状态；不得把模板建议自动写成项目事实。

### 6.3 与现有入口的接入

首批不新增快捷命令，优先扩展既有入口：

- `ui-prototype-exploration` 在命中参考分析时按 scope 读取核心知识文件。
- `22-ui-prototype-exploration` 先生成或核对 reference analysis，再进入页面、流程和视觉候选。
- `ui-prototype-exploration-template` 的 `UI-G-002` 引用项目参考分析中的选用记录。
- `frontend-experience-brief` 只接收用户已确认的体验原则，不直接复制知识库候选。
- `frontend-interaction` 引用已采纳模式、项目适配和偏离理由。
- `09` 仍只记录项目验收和证据，不验证“是否遵循某个流行产品”。

## 7. 大规模语料层的边界

母模板不应直接携带数百份第三方设计摘要或大量图片。建议达到以下任一条件后，再评估独立 Web 领域层：

- 核心目录无法在一次 scoped 读取中保持紧凑。
- 来源数量或记录数量导致 `template-sync.json` 和自检清单显著膨胀。
- 不同 Web 子领域需要明显不同的模式集和发布节奏。
- 需要抓取、全文搜索、向量检索、自动去重或许可证扫描。
- 至少两个真实项目证明外部语料层可以稳定提升设计输入质量。

届时可选：

1. 独立 `web-experience-template` 领域模板。
2. 独立只读设计知识仓，由母模板保存接入契约和版本指针。
3. 生成式索引包，母模板只同步精选摘要。

在实证前不预先创建新仓库或新同步层。

## 8. 分批实施建议

### Batch 0：双项目试点和 schema 校准

目标：不修改正式同步范围，用本提案的记录模型手工生成两份项目级参考分析。

试点应覆盖两个差异明显的 Web 场景：

- 一个开发者工具、知识工作台或数据密集型系统。
- 一个事务型表单、管理后台或面向普通用户的流程型系统。

具体试点项目与定位见 §12.1 维护者决策（`zhiyan` + `flowkit`）。第一个已评估项目只作为实例，不能单独证明通用性。试点记录重点观察：

- 模式能否跨项目复用。
- 是否能显著补齐状态、恢复、可访问性和内容设计。
- 记录字段是否过多或缺失。
- AI 是否能只读取相关记录，而不是加载全部语料。
- 采纳 / 排除理由能否被用户和后续实现理解。

版本影响：`none`，只保留研究或提案记录。

### Batch 1：发布核心知识能力 MVP

建议内容：

- 新增 §6.1 的核心文件和 reference analysis 模板。
- 至少整理 4 类来源、12 至 20 条跨项目模式；视觉和交互两类都必须有内容，不发布空目录。
- 更新现有 `ui-prototype-exploration` command / Prompt 和必要的文档生命周期指针。
- 更新 `template-sync.json`、同步脚本备用清单和 `check-template` 路径 / 关键契约断言。
- 更新 `template-docs/capability-packages.md` 的 UI 原型专项说明，不新增重复机制。
- 按发布流程更新 `VERSION`、`CHANGELOG.md` 和 `CHANGELOG-PLAIN.md`。

版本建议：`minor`。理由是新增同步目录、项目参考分析模板和派生项目可见的推荐工作流采用面。

### Batch 2：内容扩充与质量治理

建议内容：

- 基于真实项目使用反馈扩充模式，不按来源数量追求规模。
- 为候选、core、deprecated、retired 建立人工评审节奏。
- 补链接失效、证据升级 / 降级、重复模式合并和许可证检查记录。
- 只对结构、ID 唯一性、路径和必要字段做自动检查，不对长文案做脆弱字符串断言。

版本建议：若只扩内容和兼容检查，优先 `patch`。

### Batch 3：决定是否建立外部 Web 语料层

只有满足 §7 的实证门槛后才启动。该 Batch 需要独立提案，重新评估仓库归属、版本、同步、检索、许可证和维护者责任；不由本提案自动授权。

## 10. 验证与验收标准

### 10.1 提案阶段

- 明确该能力属于模板级 Web UI/UX 方法，不属于某个项目。
- 明确 `awesome-design-md` 是视觉种子来源，不是成熟交互证据库。
- 明确母模板核心层和外部大语料层的边界。
- 明确与现有 UI 探索、交互设计和原型策略的去重关系。
- 明确实施版本、同步、版权和试点要求。

### 10.2 Batch 0 试点

- 两个不同类型 Web 项目都能产出可读的 reference analysis。
- 每项推荐都能追溯到 Source / Principle / Pattern / Case ID。
- 每项推荐都说明适用、不适用、采纳状态和项目调整。
- 不能由视觉案例直接推导成熟交互结论。
- 至少覆盖主任务、状态反馈、错误恢复、可访问性和响应式，而不只覆盖颜色与布局。
- 参考分析能直接支持探索原型，且不会把候选写成已确认需求。

### 10.3 Batch 1 模板发布

- 新增文件全部进入 `template-sync.json` 和同步脚本备用清单。
- 派生项目可以通过现有 `ui-prototype-exploration` 入口发现并使用知识能力。
- 核心目录至少有 12 至 20 条经人工评审的记录，不是空 schema。
- 核心记录都有来源、证据等级、适用边界、许可策略和最后核验日期。
- `frontend-ui-reference-analysis` 能输出采纳 / 调整 / 排除矩阵及 `UI-G-002` 结论。
- `git diff --check`、Markdown 清洁检查、模板完整自检和 CI 通过。

### 10.4 效果指标

试点应记录基线和变化，不预先虚构提升比例：

- 原型前发现的遗漏状态数量。
- 被明确排除的误用模式数量。
- 设计建议具备来源和适用边界的覆盖率。
- 用户确认前后需要返工的页面、流程或状态数量。
- AI 为完成一次 reference analysis 实际读取的核心记录数量和上下文体积。

## 11. 风险与控制措施

| 风险 | 表现 | 控制措施 |
|---|---|---|
| 视觉案例被误当 UX 证据 | 从漂亮页面直接推导用户行为 | 记录类型和 A-D 证据等级分离；Case 默认不能直接成为决定 |
| 知识库膨胀 | 每个项目都同步大量无关资料 | 母模板只放精选核心；按 scope 读取；大语料层延后独立 |
| 版权和品牌风险 | 镜像截图、字体、图标或大段原文 | 默认只存元数据、自有摘要和抽象模式；逐项记录许可策略 |
| 来源失效 | 链接、版本或产品界面变化 | 记录最后核验、状态和替代来源；失效记录降级而非静默保留 |
| 双份权威 | 知识目录和项目设计各自声明事实 | 知识目录只写通用模式；项目采纳决定只写 reference analysis / 正式设计 |
| AI 机械套模板 | 忽略任务、用户和约束 | 每条记录必须写适用 / 不适用条件；项目输出必须含排除矩阵 |
| 过早自动化 | schema 尚未稳定就建检索平台 | 首批 Markdown + 稳定 ID；双项目试点后再决定机器可读格式 |
| 新流程增加负担 | 所有 UI 任务都被强制做长分析 | 只在有参考输入、视觉 / 交互方向不明确或复杂 UI 时触发；简单页面可写豁免 |
| 项目经验污染模板 | 将某实例的业务决策写成通用原则 | 只抽取至少跨两个项目成立且来源清楚的模式；项目事实留在项目仓 |

## 13. 推荐决策与下一步

AI 建议维护者按以下顺序决策：

1. 接受“母模板轻量核心 + 可扩展外部语料”的总体边界。
2. 接受四类记录、十个知识维度和 A-D 证据等级作为 Batch 0 试用 schema。
3. 不新增命令，不复制完整第三方目录，不先建向量检索或独立 Agent。
4. 用一个已评估的知识 / 开发工具类项目和一个事务型 Web 项目完成双项目 reference analysis 试点。
5. 根据试点修订字段和核心记录清单，再单独确认 Batch 1 的 `minor` 实施范围。

该顺序先验证方法是否能产出更好的原型输入，再决定知识目录、同步结构和自动化规模，避免把“收集更多资料”误当成“形成可用设计能力”。
